## 一、需求与结果总结

按后端仓库 `docs/PLAN.md` 的 **M2** 验收标准，交付 uni-app 前端骨架与登录注册：

**需求**：一套代码编译三端（H5 / 安卓 App / 微信小程序·仅练习）；UI 用 wot-design-uni；
路由用 `pages.json`；HTTP 用 `uni.request` 自封装；类型从 `openapi.json` 生成；
平台差异集中封装。

**结果**：工程从零建成，**H5 与微信小程序两端构建均通过**；登录 / 注册 / 我的 /
三个静态页共 7 个页面已实现，其中认证链路**对真后端联调验证**；
E2E 黄金路径（注册→登录→进入需登录页）通过，并有红→绿两次输出。
后端契约的 8 个路径中本前端用到 6 个，覆盖率 100%。

**关键约束的遵守情况**：

- 后端零改动（未触碰 `server/**` 与后端 `docs/**`、`openapi.json`）
- 未引入 Vant 4；未硬编码任何域名与密钥
- M3–M5 尚未交付的接口（实测 404）对应页面**只做骨架**，明确提示"接口未交付"，
  **没有用假数据冒充完成**

**契约侧的诚实说明**：`/api/auth/captcha` 与 `/api/auth/register-mode` 在 OpenAPI 中
`data` 被声明为 `Record<string, any>`（字段名无静态声明）。前端做了人工窄化 + 运行时校验，
并在代码注释中标注依据来源（《技术方案》§6.2 / §8.8）。
这是"契约不足"的有据处理，**正式收敛方式是由后端把字段写进契约（提 CR）**。

## 二、模块与调用关系

```
                    ┌─────────────────────────────────────┐
                    │  页面 pages/**（只关心 UI 与交互）    │
                    └──────────────┬──────────────────────┘
                                   │ 只用 store 与 api
                    ┌──────────────▼──────────────────────┐
                    │  stores/auth.ts（Pinia，登录态唯一源）│
                    └──────────────┬──────────────────────┘
                                   │
                    ┌──────────────▼──────────────────────┐
                    │  api/auth.ts（接口函数，逐条对照契约） │
                    └──────────────┬──────────────────────┘
                                   │
        ┌──────────────────────────▼──────────────────────────┐
        │  utils/request.ts  uni.request 封装                  │
        │  · 基地址（env.ts）  · Authorization 头              │
        │  · 拆 {code,message,data}  · 错误归一化为 ApiError   │
        └───────┬───────────────────────────┬─────────────────┘
                │                           │
   ┌────────────▼──────────┐   ┌────────────▼──────────────┐
   │ utils/error-code.ts   │   │ utils/storage.ts          │
   │ 契约 §6.1 错误码→文案  │   │ 跨端存储（禁 localStorage）│
   └───────────────────────┘   └───────────────────────────┘

   utils/platform.ts —— 剪贴板 / 外部链接（#ifdef 集中处，M3 网盘功能用）
```

**分层约定**：

- 页面**不直接**调 `uni.request`、不直接读写 storage、不出现 `#ifdef`
- 平台差异**只允许**出现在 `utils/`（ADR-0011 的硬要求）
- 类型只见于 `api/types.ts` 出口，禁止业务代码直接 import 生成物

### 2.1 请求层的错误分类（设计要点）

`ApiError` 把失败分成三类，调用方无需分辨来源：

| kind | 含义 | 典型场景 |
|---|---|---|
| `business` | 拿到统一响应体但 `code !== 0` | `1001` 用户名已存在、`1003` 验证码错误 |
| `http` | HTTP 异常且响应体不是统一响应体 | Nginx 502 的 HTML 页、网关限流页 |
| `network` | 请求未到达服务端 | 断网、后端未启动、超时 |

配套两条规则：**401 清登录态、403 不清**（403 是"已登录但无权限"，
清了会把用户无故踢下线，是常见实现错误）。

### 2.2 契约一致性的防线（本工程最重要的一块）

前端是独立仓库，无法在构建时读取后端 `openapi.json`，因此工程内保存**快照**并据此生成类型。
风险是"后端改了、快照没更新"，所以做了两件事：

1. `scripts/check-contract.mjs` —— 对比快照与**在线** `/v3/api-docs`，
   比对**结构**（路径/方法/schema/版本）而非字节（后端导出与仓库快照有 1 字节行尾差异，
   按字节比对会永远误报，报警一旦不可信就会被忽略）。漂移时 exit 1 并列出差异。
2. `scripts/test-contract-drift.mjs` —— **变异测试**：往快照注入一个后端没有的路径，
   期望检测脚本报出漂移。用途是防止校验脚本退化成"永远返回通过"的假绿。
   （思路来自后端仓库 `agents/工作计划.md` §6.5.1「防假绿前置断言」。）

## 四、实施方案与关键决策

### 4.1 工具链验证（先做，因为它决定后面能不能做）

任务书提示 Node 26 偏新、uni-app 工具链未在本项目验证过。实测结论：**兼容**。
但过程中确定了三件必须写进配置的事（详见 `lw长期记忆.md` §2）：
`vite` 锁 `5.2.8`、`@dcloudio/*` 同版本号、**不加 `"type": "module"`**。

### 4.2 验证码与 E2E（本任务最难的一环）

图形验证码的存在意义就是阻止自动化，三条路的取舍：

- ❌ 改后端加测试模式 → 任务书 §3 禁止改 `server/**`
- ❌ OCR 识别 → 不稳定，会变成偶发变红的抖动测试
- ✅ **直读 Redis**：答案就在 `hy:captcha:{uuid}`（《技术方案》§6.2），后端零改动、结果确定

前提用 `probe-captcha.ts` 单独验证过（实测取到 TTL 300s 与答案文本），
避免让 E2E 以"验证码错误"这种误导性方式失败。

### 4.3 CORS：用 Vite 代理而不是让后端配合

实测后端**无 CORS 头、预检 403**。三种解法中选**代理**：浏览器只发同源请求，
由服务端转发，问题从根上消失，且生产由 Nginx 承担同一职责，**与生产同构**。
对应地，H5 基地址设计为**同源相对路径**（`#ifdef H5`），非 H5 端强制绝对地址。

### 4.4 不做 / 推迟的事（明确记录，避免被误认为已完成）

- **小程序端界面未做人工验证** —— 需在微信开发者工具中打开 `dist/build/mp-weixin`。
  构建产物、`touristappid`（游客模式免 AppID）、`urlCheck:false` 均已就绪，
  但"命令跑通"**不等于**界面验证通过，如实标注。
- **三份法律文本是结构模板**，需需求方确认。
- **M3–M6 页面**待后端交付接口。
