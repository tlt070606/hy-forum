## 一、这个前端是什么

详见 [`../docs/adr/0011`](../docs/adr/0011-前端改用uni-app作为唯一前端.md)（选型理由与三条硬约束）。

**本工程视角只需记住三句**：

1. 一套代码编译**三端**：H5（网站）、安卓 App、微信小程序（**仅练习，永远不上线**）。
2. 因为要编小程序，所以：**没有 DOM、没有 XHR、没有 `localStorage`** —— 这三条决定了很多写法。
3. 平台差异**只允许出现在 `src/utils/`**，页面里不出现 `#ifdef`。

## 二、模块与调用关系

```
                    ┌─────────────────────────────────────┐
                    │  页面 pages/**（只关心 UI 与交互）    │
                    └──────────────┬──────────────────────┘
                                   │ 只用 store 与 api
                    ┌──────────────▼──────────────────────┐
                    │  stores/auth.ts（Pinia，登录态唯一源）│
                    └──────────────┬──────────────────────┘
                                   │
                    ┌──────────────▼──────────────────────┐
                    │  api/*.ts（接口函数，逐条对照契约）   │
                    │  contract.ts 登记端点与就绪状态       │
                    │  types.ts 是**唯一的类型出口**        │
                    └──────────────┬──────────────────────┘
                                   │
        ┌──────────────────────────▼──────────────────────────┐
        │  utils/request.ts   uni.request 封装                 │
        │  · 基地址（env.ts）  · Authorization 头               │
        │  · 拆 {code,message,data}  · 错误归一化为 ApiError    │
        └───────┬───────────────────────────┬─────────────────┘
                │                           │
   ┌────────────▼──────────┐   ┌────────────▼──────────────┐
   │ utils/error-code.ts   │   │ utils/storage.ts           │
   │ 错误码 → 用户文案      │   │ 跨端存储（禁 localStorage） │
   └───────────────────────┘   └───────────────────────────┘

   utils/platform.ts —— 剪贴板 / 外部链接（#ifdef 集中处）
```

**分层约定（改代码时守这四条）**：

- 页面**不直接**调 `uni.request`、不直接读写 storage、不出现 `#ifdef`
- 平台差异**只允许**出现在 `utils/`
- 业务代码**只从 `api/types.ts` 导入类型**，禁止直接 import 生成物
- 登录态的**唯一源**是 `stores/auth.ts`，页面不自己存 token

### 2.1 请求层的错误分类（设计要点）

`ApiError` 把失败分成三类，**调用方无需分辨来源**：

| kind | 含义 | 典型场景 |
|---|---|---|
| `business` | 拿到统一响应体但 `code !== 0` | `1001` 用户名已存在、`1003` 验证码错误 |
| `http` | HTTP 异常且响应体不是统一响应体 | Nginx 502 的 HTML 页、网关限流页 |
| `network` | 请求未到达服务端 | 断网、后端未启动、超时 |

设计取舍：**抛异常**而不是返回 `[err, data]` 元组 —— 业务代码能顺序书写；
但因为所有错误都归一化成 `ApiError`，catch 分支不必分辨来源。

配套两条规则：**401 清登录态、403 不清**（403 是"已登录但无权限"，
清了会把用户无故踢下线，是常见实现错误）。

## 三、只在本工程里成立的几条工程决策

这些决策的**理由是本工程特有的**，所以留在这里；接口与业务事实见 `docs/`。

### 3.1 图形验证码的自动化：直读 Redis

E2E 要跑注册流程，而图形验证码的存在意义就是阻止自动化。三条路的取舍：

| 方案 | 判断 |
|---|---|
| 改后端加"测试模式" | ❌ 越界（改 `server/**`），而且是为测试改被测系统 |
| OCR 识别 | ❌ 含干扰线，会变成偶发变红的**抖动测试**，比没有测试更糟 |
| **直读 Redis 取答案** | ✅ 后置零改动、结果确定。实现见 `e2e/captcha-redis.ts`（两条命令的极简 RESP 客户端，不引 ioredis） |

前提用 `e2e/probe-captcha.ts` **单独验证过**，避免 E2E 以"验证码错误"这种误导性方式失败。

### 3.2 跨源问题：用 Vite 代理，而不是让后端加 CORS

后端**没有任何 CORS 响应头**（预检直接 403）。三种解法里选**代理**：
浏览器只发同源请求，由开发服务器转发，问题从根上消失；
而生产由 Nginx 承担同一职责，**与生产同构**。

对应地，H5 的基地址设计为**同源相对路径**（`#ifdef H5`），非 H5 端强制绝对地址。
⚠️ `vite preview` 是**独立实例**，`server.proxy` 不作用于它 —— 必须单独配 `preview.proxy`，
否则跑在产物上的 E2E 会跨源全线失败（症状见 [`lw长期记忆.md`](lw长期记忆.md) §3.3 第 12 条）。

### 3.3 工具链锁版本

- `vite` 锁 **5.2.8**、`@dcloudio/*` 全部**同一个版本号** —— uni-app 的各包版本必须严格一致。
- **不加 `"type": "module"`** —— 加了会让 `vite.config.ts` 加载失败（`uni is not a function`）。
  理由与实测报错见 [`lw长期记忆.md`](lw长期记忆.md) §3.2 第 4 条。
- Node 版本：本机实测 **v26.4.0 可用**（这曾是 M2 最大的未验证风险）。
  CI 里用 22（`setup-node` 的稳定 LTS），本流水线只跑 `npm ci` + `vue-tsc`，对 Node 大版本不敏感。

### 3.4 类型检查为什么拆成两个 tsconfig

`tsconfig` 的 `types` 是**替代**默认类型引入、不是追加。app 侧需要 `@dcloudio/types` + `vite/client`，
而 `vite.config.ts` / `playwright.config.ts` / `e2e/**` 跑在 Node 里、需要 `node` 类型。

**两边的类型环境不能混**：把 `node` 塞进 app 侧，会让小程序 / App 的代码误以为
`process`、`Buffer`、`fs` 可用（`uni` 运行时不提供这些）—— 那是**为了消错而制造下一个错**。

因此拆成 `tsconfig.json`（app）与 `tsconfig.node.json`（node），**`npm run type-check` 两侧都跑**。
⚠️ 不许把文件从 `include` 里删掉来消错：拆两个是"文件仍被检查"，删 include 是"检查被关掉"。

## 四、契约一致性：本工程的防线在哪

契约的**唯一事实来源是仓库根 [`../openapi.json`](../openapi.json)**。
本工程的做法与历史包袱：

| 环节 | 现状 |
|---|---|
| 类型生成 | `npm run gen:api`，输入是**工程内的快照** `src/api/generated/openapi.snapshot.json` |
| 快照与契约的关系 | 合并进同一仓库**之前**，前端是独立仓库，只能在工程内留一份副本 → **这是历史包袱** |
| 漂移检查 | ① 本地 `npm run check:contract`（比对快照与**在线**后端）；② **CI** `.github/workflows/ci-web.yml` 比对**仓库根 `openapi.json`** 与工程内快照 |
| 退役计划 | 契约已回到一处，快照该退役。方案见 [`../docs/agents/M3-计划与前置.md`](../docs/agents/M3-计划与前置.md) §5.1 |

另有两个**形状缺口**（`captcha` / `register-mode` 的 `data` 是 `Record<string, any>`），
本工程用"人工窄化类型 + 运行时校验"顶着。已登记 **CR-005**，由 M3 修；**修完这层临时设施才能拆**。

> **`scripts/test-contract-drift.mjs` 的意义**：它往快照里注入一个后端没有的路径，
> 期望检测脚本报出漂移。用途是防止校验脚本退化成"永远返回通过"的假绿 ——
> **一个从未失败过的检查，不能证明它在检查任何东西。**
