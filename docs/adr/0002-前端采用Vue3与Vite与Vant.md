# ADR-0002：前端采用 Vue 3 + Vite + Vant，而非 uni-app

- 状态：**已被取代**（Superseded by [ADR-0011：前端改用 uni-app 作为唯一前端](0011-前端改用uni-app作为唯一前端.md)，2026-09-14）
- 日期：2026-09-14

## 背景

候选方案有两个：uni-app（可编译到多端，含原生 App），或纯 Web 栈（Vue 3 + Vite + Vant）。

## 决策

采用 **Vue 3 + Vite + TypeScript + Vant 4 + Pinia + Vue Router + Axios** 的纯 Web 方案，安卓端用 WebView 壳承载。

## 理由

1. uni-app 本身即基于 Vue 3 + Vite + TS，两者不是对立语言栈，真正差异只在「能否编译出原生 App」。
2. 项目已明确**不做微信小程序**，uni-app 仅剩「原生 App 打包」这一优势。
3. 论坛的核心交互是信息流滚动、图片九宫格与楼层评论，纯 Web 实现体验已足够。
4. **决定性因素是热更新**：纯 Web 方案下代码更新后用户刷新即生效；原生 App 每次改动都要求用户重新下载安装包，对一个持续迭代的项目不可接受。
5. Vant 的移动端组件生态与调试体验优于 uni-app。

## 后果

- 无法使用原生推送与原生相册多选上传。
- 若未来必须上架应用商店或需要原生推送，需迁移到 uni-app；届时页面代码可大量复用，仅需替换 UI 组件层与平台适配层。

## 取代说明（2026-09-14）

本 ADR 的**理由 1、2、3、5 依赖同一个前提：「项目不做微信小程序」**。该前提于 2026-09-14 被需求方推翻（要增加小程序端用于练习），因此本决策失效，由 [ADR-0011](0011-前端改用uni-app作为唯一前端.md) 取代。

需要说清的是**哪些部分并未过时**：

- **理由 4（热更新）仍然成立，而且不构成对 uni-app 的反对** —— H5 与小程序都不需要用户重装；原方案里安卓端用 WebView 壳加载线上站点，本身也是热更新。详见 ADR-0011「理由 4」。
- **理由 3（论坛的核心交互用 Web 实现足够）也仍然成立** —— uni-app 本身就是 Web 技术，只是多了一层跨端编译。
- 被推翻的是**结论**（选纯 Web 栈），不是这些判断本身。这也是为什么迁移成本不高：页面逻辑可复用，主要换 UI 组件层与平台适配层（原文在"后果"里已经预见了这一点）。
