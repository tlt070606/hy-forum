# ADR-0005：注册模式可配置，并以邀请制作为降级方案

- 状态：已接受
- 日期：2026-09-14

## 背景

产品是**公开 UGC 论坛**，按《互联网论坛社区服务管理规定》需向网信部门备案。
需求方为个人主体，备案能否办下来存在不确定性；需求方已确认接受「邀请制 / 不公开推广」作为降级方案。
同时需求方希望默认仍能公开注册。

## 决策

将注册模式存入 `sys_config` 表的 `register_mode` 配置项，取值为：

| 取值 | 行为 |
|---|---|
| `open`（默认） | 任何人可注册，需通过图形验证码 |
| `invite` | 必须提供有效邀请码才能注册 |
| `closed` | 完全关闭注册，仅保留已注册用户登录 |

配套新增 `invite_code` 表管理邀请码；前端通过 `GET /api/auth/register-mode` 动态渲染注册表单。

## 理由

1. 把「合规降级」从**运营决策**变成**配置开关**，切换不需要改代码、不需要发版，也不需要停机。
2. 邀请制相比「直接关闭注册」，能保留小范围拉新的能力，更适合降级场景。
3. ~~邀请码校验依赖 `uk_code` 唯一索引 + 同事务置位，天然防并发重复使用。~~ **该说法有误，已修订（P1-4，2026-09-14）**：`uk_code` 只保证 **code 不重复**，**不保证不被使用两次**；「先 `SELECT` 查 `status=0` 再 `UPDATE`」在 RC/RR 下两个并发事务都可能成功。正确写法是**条件更新 + 影响行数校验**（影响行数必须为 1），详见 [`../技术方案.md`](../技术方案.md) §8.8。这条错误正是"看起来有保障、实际没有"的典型，已由 `M6_invite_code_single_use_concurrent` 测试覆盖。

## 后果

- 多出 `sys_config`、`invite_code` 两张表，以及一个注册模式查询接口。
- 邀请码校验逻辑会进入注册主流程，需保证在 `open` 模式下**零额外开销**（先判模式再校验码）。
- 管理员账号不受注册模式影响。
