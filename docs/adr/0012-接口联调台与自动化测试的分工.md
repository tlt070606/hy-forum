# ADR-0012：Apifox 作为人工联调台，自动化测试仍留在仓库内

- 状态：**已接受。** §6 的岔路经需求方选定为**方案 A**（2026-09-14）
- 日期：2026-09-14
- 触发：需求方提议「可以基于 Apifox 来构建自动化测试」
- 相关：[`../testing/README.md`](../testing/README.md) §3 工具链 / §4 CI 流水线、[`../agents/工作计划.md`](../agents/工作计划.md) §4 广播区

---

## 1. 背景：先核对现状，因为这个提议里混了两件事

在动手前核对了仓库，得到一个容易搞混的结论：

> **本项目已经有接口层自动化测试，而且它不在 Apifox 里。**

| 项 | 现状 | 证据 |
|---|---|---|
| 接口层自动化测试 | **已有**。REST Assured 打真实 HTTP（随机端口起应用） | `server/src/test/java/com/hyforum/auth/` —— 7 个测试类：`M1CaptchaTest`、`M1ErrorCodesTest`、`M1ResponseEnvelopeTest`、`M1LogoutTest`、`M1RegisterLoginMeFlowTest`、`M1RegisterModeTest`、`M1SecurityBasicsTest`；加支撑类 `AuthApiTestSupport` |
| 谁在跑它 | `mvn test`，CI 的第 2 步 | [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) 第 182–190 行 |
| 工具链里登记了吗 | 已登记：「接口测试 = REST Assured / MockMvc，**对齐 `openapi.json`**」 | [`../testing/README.md`](../testing/README.md) §3 |
| 契约在哪 | 仓库根 `openapi.json`（8 个路径），**任何人不得手工编辑** | [`../agents/工作计划.md`](../agents/工作计划.md) §4 广播（2026-09-14） |
| 尚未接入的 | 「黄金路径 E2E」目前只有注释，没有步骤 | `ci.yml` 第 274–280 行 |

所以需求方的提议**不是"从零加一层自动化测试"**，而是把两件不同的事说成了一件事：

- **(甲) 联调台** —— 人要打开一个界面，点几下就发出请求、看响应、**把请求存下来复用**。
  Swagger UI 只能「看」，不能「存」；而且它依赖应用正在运行。需求方这次打不开 `http://localhost:8080/swagger-ui/index.html`，正是踩在这一条上（应用没起时它当然不通）。
- **(乙) 自动化回归** —— 无人值守、可重复、进 CI、**能在别人 clone 下来的机器上跑**。

Apifox 在 (甲) 上明显强于现状。在 (乙) 上它有一个绕不开的问题：**它的用例默认存在云端账号里，不在仓库里。**

---

## 2. 决策

1. **Apifox 定位为「人工联调台」**，不作为测试的事实来源。
2. **自动化测试的唯一位置仍是仓库内代码**：接口层用已就位的 REST Assured；后续 E2E 用 Playwright（§3 工具链已登记）。
3. **契约的唯一来源仍是仓库根 `openapi.json`。** Apifox 只允许**导入**它。
4. **除非需求方在 §6 选 B，否则不为 Apifox 增加任何 CI 步骤。**

---

## 3. 红线（无论 §6 选哪条都成立）

| # | 红线 | 违反的后果 |
|---|---|---|
| **R-A** | **禁止在 Apifox 里手工新增/修改接口定义**；也**禁止**把 Apifox 导出的 OpenAPI 回写仓库 | 立刻出现第二份契约。前端 Agent 会按 Apifox 那一版写代码，与 `openapi.json` 漂移，而且**漂移不可察觉**。这与铁律 1 同源，本项目已经因为"副本漂移"吃过一次亏 |
| **R-B** | **禁止把 Apifox 访问令牌写进仓库**。若将来 CI 用 `apifox-cli`，令牌只走 GitHub Secrets | 铁律 5（禁止硬编码密钥） |
| **R-C** | **CI 当前是红的、根因尚未定位。在定位之前不要往 `ci.yml` 加任何新步骤（含 Apifox）** | 在已知失败的流水线上再叠一步，等于制造两个未知数，之后谁也说不清是哪一步坏的 |
| **R-D** | 在 Apifox 里调试产生的数据（测试用户、测试帖）**只允许发往本地开发库或测试库** | 打到开发库会污染管理员账号与 seed 数据 |

---

## 4. 理由

1. **「能在别人机器上跑」是自动化测试的硬指标。** Apifox 的用例在云端账号里 —— 换台机器、换个人、离线，clone 仓库拿到的是空场景。仓库内代码天然满足这条，且它已经是既成事实。
2. **契约已经集中在一处。** Apifox 导入 `openapi.json` 是顺向消费，零冲突；一旦反向导出就开始打架。
3. **分层不重复。** 联调台解决"人怎么方便地发一个请求"，自动化解决"无人值守回归"。用两个工具并不可怕，**同一个东西存两份才可怕**。
4. **成本几乎为零。** Apifox 当联调台不需要碰 CI、不需要碰后端、不需要改契约，收益立刻兑现。

---

## 5. 代价（承认，不掩饰）

- 需求方想看**图形化的绿色对勾报告**，就得在 Apifox 里编排场景；而那份成果**不在仓库里**，交给另一个 Agent 时传不过去 —— 这恰好与需求方"要产出物、要能交接"的诉求相反。
- 现有接口测试是 Java 代码，**需求方本人不便阅读和修改**。这**正是 Apifox 的吸引力所在**，本决策没有解决它，只是把它归到「联调台」这一类里。
- 若需求方选了 §6 的方案 B，就要接受额外代价：CI 依赖 Apifox 云与其可用性、需要账号令牌、需要先把应用在 CI 里跑起来（CI 时间上升）。

---

## 6. 已定的岔路：方案 A

需求方于 2026-09-14 选定 **A**（Apifox 只做联调台，自动化测试留在 `mvn test`）。

| 方案 | 内容 | 改动量 | 优点 | 缺点 |
|---|---|---|---|---|
| **A（已选定）** | Apifox 只做联调台；自动化留在 `mvn test` | **零** | 不引入任何新依赖，契约单写者不变 | 自动化测试报告不是图形化的 |
| B | A + 用 Apifox 跑自动化（场景导出进仓库 + CI 调 `apifox-cli`） | 中 | 图形化编排与报告 | 依赖 Apifox 云；需令牌；CI 要先起应用；**须先解决 R-C** |
| C | 不用 Apifox，改用仓库内纯文本请求集（`.http` 文件，VS Code REST Client / IntelliJ HTTP Client 直接可用） | 小 | 进仓库、无云依赖、**Agent 能读能改能生成**、可接 CI | 没有 GUI 的环境变量与断言编排，比 Apifox 简陋 |

**B 与 C 未被否决，只是没选。** 若将来出现「需要图形化回归报告」或「需要用 GUI 编排多接口串联」的真实需求，再回来重新评估 —— 但**不要同时上两条链路**：多一条链路就多一份会漂移的东西，而本项目刚因为副本漂移付过一次代价。

## 7. 未验证项（不要当已确认事实用）

| 项 | 状态 | 怎么确认 |
|---|---|---|
| Apifox 免费版对「自动化测试 / CLI」的额度限制 | **未核实。** 只检索到厂商自述与第三方文章，没有拿到权威额度表，因此本节不做任何承诺 | 需求方登录 Apifox 查看定价页 |
| Apifox 能否把测试场景**完整**导出为可提交进仓库的文件（含步骤编排、断言、提取变量） | **未核实。** 存在导出能力，但格式与完整性没验证 | 需求方建一个 2 步场景试导出一次即可判定 |

> 方案 B 成立与否，取决于这两条。**在核实之前不要按 B 投入。**

---

## 8. 若采用方案 A：接入步骤（可直接执行）

1. 启动后端（见 [`../交接说明.md`](../交接说明.md) §1）。
2. Apifox → 新建项目 → **导入数据** → OpenAPI/Swagger → 选「URL 导入」填
   `http://localhost:8080/v3/api-docs`，或选「文件导入」用仓库根 `openapi.json`。
3. 建环境，设 `baseUrl = http://localhost:8080`；登录后拿到的 token 放共享变量，供其他接口引用。
4. **导入之后不要再编辑接口定义**（§3 R-A）。接口变了就重新导入一次。
