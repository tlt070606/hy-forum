# ADR-0004：部署采用双档位（lowmem / standard）

- 状态：**已被取代**（Superseded by [ADR-0010：部署以本地开发为基准，取消部署档位](0010-部署以本地开发为基准并取消档位.md)，2026-09-14）
- 日期：2026-09-14

## 背景

需求方现有阿里云服务器规格为 **2 vCPU / 2 GiB**（Ubuntu 22.04、ESSD 40 GiB）。
在此规格上同时运行 Nginx + Spring Boot + MySQL 8 + Redis 属于临界配置，存在 OOM 风险。
需求方**暂不打算升配**（成本原因），但希望保留提升性能的余地。

## 决策

采用**双档位部署**：

- **Profile B `lowmem`**：当前落地档位，针对 2 vCPU / 2 GiB 做极限调优。
- **Profile A `standard`**：升配后使用，面向 4 vCPU / 8 GiB。

**两者的应用代码完全相同**，差异仅通过 `.env` 与 `docker-compose.<profile>.yml` 注入。

## 理由

1. 避免为低配环境维护一套独立代码分支 —— 那是长期的维护负担与缺陷来源。
2. 需求方明确「有性能更高的就用更高的，但暂不升配」，双档位正好匹配这种渐进式演进的诉求。
3. 切换成本极低：改一个环境变量并重启容器，数据卷不变。

## 后果

- 所有会影响资源占用的参数（缓冲池大小、连接数、JVM 参数、限流阈值、缓存开关）都必须**外置为配置**，禁止硬编码。
- 应用层需为低配做自适应：列表接口只返回摘要、分页上限 20、列表页只用缩略图、首屏不并发请求。
- **必须配置 2G swap**；**禁止在服务器上执行构建**（`mvn package` / `npm run build` 内存峰值均超过 1G）。
- 内存预算余量约 **226M**（v1.4 按**进程峰值**重算后的真实值）。v1.3 曾写「余量仅约 320M」，那是「容器上限相加」得出的名义值，且当时 backend 640M 小于其自身 JVM 参数之和 —— 即那 320M 余量并不存在。新增任何常驻进程前都必须重新评估。
- 详见 [`../ops/deployment.md`](../ops/deployment.md)。
