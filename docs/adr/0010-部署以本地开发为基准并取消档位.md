# ADR-0010：部署以本地开发为基准，取消部署档位

- 状态：已接受
- 日期：2026-09-14
- 取代：[ADR-0004 部署采用双档位（lowmem / standard）](0004-部署双档位.md)
- 依据：方案评审 **D4 决策**（见 [`../review/2026-09-14-方案评审记录.md`](../review/2026-09-14-方案评审记录.md) §10）

## 背景

1. ADR-0004 的前提是需求方「**暂不升配服务器**（成本原因），但希望保留提升性能的余地」，因此设计了 lowmem / standard 双档位（差异只允许出现在 `.env` 与 compose override）。
2. 2026-09-14 方案评审中，需求方对该前提给出新的明确表述：
   > 「其实，这个我本来想在服务器上部署的。如果不行的话，仅仅作为测试练习，在本地开就行了。**你先要保证它的性能可以实现**，如果要做衰减的话，我后续再衰减吧，**不用开两个版本**。」
   并在 D4 澄清中确认：**先按本地开发为准，上线时间后、升配后再上**；**取消档位机制，只留一份 compose 与一份参数**。
3. 评审同时得出一个事实纠正：**2 vCPU / 2 GiB 并非「跑不动」**。v1.4 按进程峰值重算后该规格余量约 226M，在 20–30 并发 / QPS 50–100 的低并发下可用，代价是**没有冗余**。因此本决策不是「2G 不可用」，而是**主动选择不在开发期承受低配约束**。

## 决策

1. **开发期以本地为基准**，不设内存约束；开发用 `localhost`，不依赖域名、备案与 HTTPS。
2. **取消部署档位机制**：不再维护 `docker-compose.lowmem.yml` / `docker-compose.standard.yml` 与 `APP_PROFILE` 环境变量；只保留**一份** `docker-compose.yml`、**一份** `.env`、**一份**容量参数表。
3. **上线目标改为「升配后的服务器」**，规格与时间待定（登记为 `PLAN.md` §6 Q4）。
4. **上线前必须先回填规格、复算参数并回填 `ops/deployment.md`**；不允许拿未复算的参数上生产。
5. 原 2C2G 的参数核算结果**不删除**，转为 `ops/deployment.md` **附录 A「应急参数集」**；仅当最终部署规格可用内存 < 4 GiB 时启用。
6. `AGENTS.md` **不做修改**：铁律 2（零代码分叉）在单一配置下自动满足；铁律 6（禁止在服务器上构建）继续有效，其依据是构建期内存峰值，与档位机制无关。
7. 配套文档动作：`PLAN.md` §2 #11 废止、§3 A1／A9 修订、§1.1 #15 与 M8 交付物／验收改写、R14 改写、新增 Q4 与关闭项 C9。

## 理由

1. **先证明「能做到什么」，再在真实规格上取舍。** 反过来（先按最低配写死）会把大量精力耗在参数微调上，而且容易掩盖真正的性能问题。
2. **档位机制的收益与成本不对称。** 收益是「同一产物换配置即可降级」，成本是**每一个容量参数都要维护两套值**，且低配那一套在开发环境**永远不被执行、无法被测试覆盖** —— 这本身就是缺陷来源。
3. **档位机制所服务的场景当前不存在。** 它的价值在于「立刻上线到小机器」，而上线时间已推迟到升配之后。
4. **需求方明确要求「保证性能可以实现」**，其含义是不要在开发期自我设限。

## 后果

- **负面：上线时出现一次性集中决策。** 规格、参数、是否启用附录 A，全部后置到上线前完成；若届时才发现在目标规格上跑不动，返工窗口很小。**这是本决策的主要代价**，已通过 `deployment.md` §6「参数复算触发条件」与上线检查清单部分对冲。
- **附录 A 的参数未经真机验证**（v1.4 是按进程峰值推算的）。若最终启用，必须先实测回填，尤其是 Metaspace。
- 开发机需要能承受统一参数（约 2–3 GiB 可用内存），这是「不设约束」的隐含成本。
- 若将来真的需要档位机制（例如同时维护线上与演示两套不同规格），**必须新开 ADR**，不能靠临时加环境变量复活 —— 那正是 ADR-0004 试图避免的维护负担。
- 与档位无关的约束全部保留：本地构建／CI 出产物（铁律 6）、图片走 OSS + CDN、服务端签名直传（铁律 8）、访问日志 ≥ 6 个月与审核留痕 ≥ 6 个月（合规 C6／C9）。
