# ADR-0009：评论采用两层「贴吧式」结构

- 状态：已接受
- 日期：2026-09-14

## 背景

需求方确认帖子形态为「贴吧式」，即：有版块、有标题，评论包含主楼与楼中楼。
需要决定评论的层级上限与表结构。

## 决策

采用**两层**结构，用 `parent_id` + `root_id` 两个字段表达：

| 场景 | `parent_id` | `root_id` |
|---|---|---|
| 主楼（直接评论帖子） | 0 | 0 |
| 楼中楼（回复主楼） | 主楼 id | 主楼 id |

**强制约束**：若提交的 `parentId` 指向的是楼中楼（即其 `parent_id != 0`），后端**一律将其归并到该楼所属的 `root_id`**，从而杜绝三层结构。

## 理由

1. 贴吧的实际交互就是两层：主楼 + 对主楼的回复，不再无限嵌套。
2. 两层结构下查询简单：主楼列表 `WHERE post_id=? AND parent_id=0`；楼中楼 `WHERE root_id=? AND parent_id!=0`，两者都可走索引。
3. 无限层级嵌套在前端渲染与分页上都非常复杂，收益极低。
4. 「回复楼中楼」时归并到根楼，既保留了 @某人的语义（`reply_to_user_id`），又不产生第三层。

## 后果

- `reply_to_user_id` 用于在 UI 上显示「回复 @某某」。
- 主楼维护 `reply_count`，用于展示「共 N 条回复」。
- 楼中楼默认只展示前 2 条，其余点击展开。

## 定案补充（2026-09-14，评审遗留项 P1-3）

原 ADR 的表述留下了一个歧义：**「归并到 `root_id`」之后，`parent_id` 到底存什么值？** 两种读法会导致完全相反的结论：

- 读法 (a)：归并后 `parent_id` **也指向主楼** → 楼中楼的 `parent_id` 恒等于 `root_id`，三层在数据上**不可能被表达**；
- 读法 (b)：`parent_id` **保留指向被回复的楼中楼**，只用 `root_id` 记主楼 → 三层**可以表达**，"杜绝"完全靠应用逻辑。

**定案：采用读法 (a)。**

| 场景 | `parent_id` | `root_id` |
|---|---|---|
| 主楼 | 0 | 0 |
| 楼中楼（含"回复某条楼中楼"） | 主楼 id | 主楼 id |

**理由**：只有 (a) 能给出**机械不变量**，从而真正做到"杜绝"而非"约定"。(b) 下三层是可表达的，`CHECK` 帮不上忙，任何一处漏校验就会长出三层结构。

**由此产生的两点后果**：

1. `root_id` 对楼中楼而言与 `parent_id` 恒等，**看起来冗余，但不能删** —— `GET /api/comments/{rootId}/replies` 只带 `rootId`，若仅靠 `parent_id` 查询则必须同时提供 `post_id` 才能用上 `idx_post_root`。保留 `idx_root(root_id, created_at)` 才有可用的索引。
2. 数据库 `CHECK`（`chk_comment_two_levels`）**只保证同一行内两列的关系**，无法证明 `root_id` 指向的行确实是主楼（本项目禁用外键，`CHECK` 不能跨行引用）。因此「跨行校验」必须在**唯一写入口**完成，且**禁止任何其他代码路径直接 `INSERT comment`** —— 这是架构要求，见 [`../技术方案.md`](../技术方案.md) §6.6。

**验证**：`M4_comment_no_third_level`（含对抗性用例：对楼中楼再回复、伪造 `parentId` 指向楼中楼）。
