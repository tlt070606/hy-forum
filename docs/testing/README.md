# 测试策略

> 本文件是**测试的唯一依据**。派活、写测试、验收前必读。
> 验收标准的来源永远是 [`../PLAN.md`](../PLAN.md) §4 与 [`../技术方案.md`](../技术方案.md) §8／§10；
> 本文件只规定**怎么测**，**不重定义验收标准**。

---

## 0. 第一原则

> **测试从「验收标准」反推，不从「实现」反推。**

`PLAN.md` §4 的验收标准是用自然语言写好的测试用例。实现者若从自己的代码反推测试，只会验证"我写的就是我写的"。
对照表见 [`验收项-测试映射.md`](验收项-测试映射.md) —— **每条验收项都必须有对应测试方法名**。

---

## 1. 三道防线（关键是分离）

| 防线 | 谁做 | 给它什么 | 抓什么 | 风险 |
|---|---|---|---|---|
| **① 实现者自带** | L2 | 全部信息 | 单元、边界、分支 | **与实现共谋**：同一个误解同时写进实现和测试 |
| **② 独立测试 agent** | L3 | 契约 + 代码，**不给 ① 写的测试** | 接口行为、业务不变量 | 可能测不到深层逻辑 |
| **③ 对抗性验证 agent** | L3 | **只要契约**（可以不给实现） | 并发、绕过、越权、状态机漏洞、边界 | 需要人类判断反例是否真实 |

**硬规则：②③ 不得读取 ① 的测试代码。** 否则会被同样的假设"带偏"，防线就不独立了。

---

## 2. 三条纪律（比写多少测试重要）

### 纪律一：给清单，不给"帮我写测试"

任务书里逐条列出 **测试方法名 + 断言 + 对应验收项编号**（清单直接取
[`验收项-测试映射.md`](验收项-测试映射.md)）。模糊指令的产物通常是 `assertTrue(true)` 式的装饰品。

### 纪律二：要"红 → 绿"两次输出

强制 TDD 顺序，并要求把两次命令输出都贴在交付报告里：

```
先写测试 → 跑 → 贴出【失败】输出 → 写实现 → 跑 → 贴出【通过】输出
```

> **一个从未失败过的测试，不能证明它在测任何东西。**

这是过滤"假测试"最有效的手段。

### 纪律三：用变异测试验收测试本身

派一个 L3 agent **故意改坏实现**，然后跑测试，看是否变红：

| 变异点（示例） | 期望 |
|---|---|
| 把审核置位 `status=0` 改成 `status=1` | `M5_post_pending_hidden` 必须变红 |
| 把邀请码的条件 UPDATE 改回"先查后写" | `M6_invite_code_single_use_concurrent` 必须变红 |
| 去掉 `parent_id` 归并逻辑 | `M4_comment_no_third_level` 必须变红 |
| 把 `like_count` 的增减去掉 | `M4_like_idempotent_concurrent` 必须变红 |

- **变红 → 测试有效**；**没变红 → 该测试是废的，返工重写。**
- 手工做 5 个变异点即可（也可上 `pitest`，但手工版对学习价值更高）。
- 这是**唯一能证明"测试真的在测东西"**的手段。

## 3. 工具链

| 用途 | 选型 | 说明 |
|---|---|---|
| 集成测试环境 | **本机 MySQL 独立测试库 `hy_forum_test` + VM 内 Redis**（`192.168.100.128:6380`） | **不使用 Testcontainers**，理由、代价与补偿见 §3.1 |
| 属性测试 | **jqwik** | 对幂等/并发类不变量强于手写用例。例：「任意调用序列下，`post_collect` 行数 == 去重后的 `(post_id,user_id)` 组合数」 |
| 架构约束 | **ArchUnit** | 铁律 3（禁跨模块调用）、铁律 7（禁重组件依赖） |
| 接口测试 | REST Assured / MockMvc | 对齐 `openapi.json` |
| 前端 E2E | **Playwright** | 支持移动端设备模拟；能用从 `openapi.json` 生成的 mock 独立跑 |
| 前端类型 | `openapi-typescript` / `orval` | 从 `openapi.json` 生成类型，**契约变了前端就编译报错** |
| 变异测试（可选） | pitest | 慢，放 nightly |

### 3.1 为什么不用 Testcontainers（决策、代价与补偿）

**背景**：本机 Windows **未安装 Docker Desktop**（[`../ops/deployment.md`](../ops/deployment.md) §3）。装它会引入 WSL2/Hyper-V 这一层虚拟化，**拖慢正在运行的 VMware 虚拟机**。经权衡（2026-09-14 D6 决策），**放弃 Testcontainers**。

**代价（必须承认，不要自欺）**：

1. **失去容器级隔离** —— 测试之间会互相污染，并行测试更容易互相干扰。
2. **本地与 CI 环境不一致** —— 本地是常驻 MySQL 实例，CI 是临时实例。

**补偿措施（三条，缺一不可）**：

1. **每次运行前重建测试库**：`powershell -File scripts/init_test_db.ps1 -User root -Password '***'`
   （DROP + CREATE；**DDL 从 `docs/db/schema.sql` 派生，只替换库名，不维护第二份建表脚本**）
2. **测试内自行清理**：优先用 `@Transactional` 自动回滚；对**并发/多线程**测试（事务边界不同，回滚无效）改为显式 `@BeforeEach` 清表。
3. **CI 侧用 GitHub `services: mysql` + `services: redis`** —— 效果**等价于 Testcontainers**，且不需要本地 Docker（GitHub runner 自带 Docker daemon）。

> **结论**：「全自动化」这个目标不受影响 —— 隔离层从「容器」下移到「独立库 + 清表」，而 CI 侧依然享有临时实例。**但本地测试的"干净起点"从此依赖于"先跑 init_test_db"这个动作**，所以 CI 流水线的第一步必须包含它。

## 4. CI 流水线（按耗时排序）

> **铁律 6 说明**：CI 跑在 GitHub 的机器上，**不是项目服务器**，因此不违反"禁止在服务器上构建"，
> 而且铁律本身就建议使用 CI。

```
1. 重建测试库（DDL 由 schema.sql 派生）→ 0 错误
   ├─ 表数 = 16
   ├─ 字符集全部 utf8mb4
   ├─ 外键数 = 0（docs/db/README.md 规范）
   └─ chk_comment_two_levels 存在且强制
2. mvn test（含 ArchUnit：铁律 3 / 铁律 7）—— CI 侧用 GitHub `services: mysql` + `services: redis`
3. openapi.json 漂移检查：重新导出并与仓库比对，不一致 → 失败
4. 前端 tsc --noEmit + 生成的类型是否为最新
5. 黄金路径 E2E（REST Assured / Playwright）
6. 变异测试（nightly，不阻塞 PR）
7. 铁律审计（workflow 扇出）：无硬编码密钥（铁律 5）、无重组件依赖（铁律 7）
```

## 5. 命名与防漏测

**测试方法名必须带验收项编号**，例如：

```
M4_like_idempotent_concurrent
M5_edit_post_resets_to_pending
C9_log_retention_not_shorter_than_6_months
SEC_cannot_edit_others_post
```

好处：可以写个脚本对比 [`验收项-测试映射.md`](验收项-测试映射.md) 与测试方法名，
**自动查出「哪条验收项还没有测试」**。

> 这比代码覆盖率有意义得多：覆盖率 90% 也可能一条业务规则都没验证过。

### 5.1 两个已实测的坑（不记住就会白写）

**坑一：Surefire 默认不跑 `*IT.java`。**

Maven Surefire 的默认 include 是 `**/Test*.java`、`**/*Test.java`、`**/*Tests.java`、`**/*TestCase.java` —— **`*IT.java` 不在其中**（那是 Failsafe 插件的约定，本项目没有配 Failsafe）。

后果很隐蔽：你把集成测试命名成 `PostLikeIT.java`，`mvn test` 会**静默跳过**它 —— 测试全绿，但那条测试**从没执行过**。这跟"只测拒绝不测接受"是同一类骗人方式：绿得毫无意义。

**规矩：本项目的测试类一律以 `Test` 结尾**（如 `M1CaptchaTest`、`SchemaInvariantTest`）。不要用 `IT` 后缀。如果将来确实要用 Failsafe 分离集成测试，必须同时改 CI 并在本文件登记。

**坑二：`@Valid` 参数校验发生在 Controller 方法体之前。**

想测限流返回 `429` 时，如果发的请求体不合法，参数校验会**先**返回 `400`，你永远不会走到限流逻辑，于是"限流没生效"这个 bug 会被测试掩盖。

**规矩：测限流/越权/业务分支时，一律使用 `§6` 契约允许的合法请求体**，只把要触发的那一个条件（如请求次数、token）改掉。

## 6. 时序要求

**测试基建必须在 W1 建好**（见 [`../agents/README.md`](../agents/README.md) §4）：

- Testcontainers 配置
- 一个幂等测试样板（后面所有模块照抄）
- CI 骨架
- 黄金路径脚本的骨架

否则到 M4 又要重造轮子，而且每个 agent 会写出风格完全不同的测试。
