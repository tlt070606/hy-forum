# 前端 Agent 开工说明（每次派前端任务前看这一份）

> **这份文件回答一个问题**：以后要写前端，**在哪个目录开 Agent、给它什么、谁验收**。
> 它不是任务书 —— 任务书在 [`tasks/`](tasks/)，`web/**` 的规则在 [`README.md`](README.md) §1.1 与 [`工作计划.md`](工作计划.md) §2。
>
> 日期：2026-09-15

## 1. 一句话答案

| 问 | 答 |
|---|---|
| **在哪个目录开 Agent** | **仓库根 `D:\demo\Hy论坛`**（**不是** `web/`） |
| **它的写权范围** | `web/**`（**只**这一块） |
| **它必须能读到的** | 仓库根 `openapi.json`、`docs/agents/工作计划.md` §4、`docs/技术方案.md` §6、它自己的任务书 |

### ⚠️ 为什么不能只在 `web/` 里开

因为**它必须读得到 `web/` 之外的四样东西**：

| 要读什么 | 在哪 | 不读会怎样 |
|---|---|---|
| **广播区**（谁改了契约、有什么新坑） | `docs/agents/工作计划.md` §4 | 它会照着过期的事实干活 |
| **契约的唯一事实来源** | 仓库根 `openapi.json` | 它会去猜接口形状 → 编造字段 |
| 接口的字段级说明与错误码 | `docs/技术方案.md` §6／§6.1 | 同上 |
| **任务书** | `docs/agents/tasks/*.md` | 它会自由发挥 |

> **唯一写者看板的入口在仓库根。** 上一个前端 Agent 之所以干得好，不是因为它开在哪个目录，
> 而是因为它拿到了任务书、并且自己去读了后端仓库的 `AGENTS.md` 与看板 §6.5.1。
> **它在独立仓库里，靠"手工搭的指针"读到了这些** —— 现在合并了，这些指针应该变成它的标准开工动作。

## 2. 直接复制粘贴的提示词（派前端任务时用这个模板）

任务书是主体，下面是**这段话本身**（不是任务书的替代）：

```text
你是 L2 前端实现者。工作目录：D:\demo\Hy论坛

开工前按这个顺序读，读不完不许动手：
1. docs/agents/tasks/<你的任务书>.md     ← 这是你的完整任务范围与验收标准
2. docs/agents/工作计划.md  §4 广播区     ← 每一条都读，那里有别人踩过的坑
3. docs/agents/README.md   §1.1 与 §7     ← 前端 L2 的硬限制 + 本机工程陷阱
4. web/README.md 与 web/lw长期记忆.md     ← 前端的工程约定与实测坑清单
5. openapi.json（仓库根）                  ← 接口契约的唯一事实来源

你的写权：web/**  —— 只这一块。
禁止：
  · 改 openapi.json、docs/**、server/**、.github/workflows/**
  · 读 server/src/main/java/**（理由见 docs/agents/README.md §1.1：
    给了实现你就会去读代码"猜"契约的意图，契约的歧义就永远暴露不出来）
  · 手改 web/src/api/generated/**（那是从契约生成的）
  · 发现契约不足就自己编形状 —— 要停下来提 CR

交付时必须贴真实命令输出，至少包含：
  · npm run type-check            （红→绿两次输出）
  · npm run check:contract        （契约一致性）
  · npm run build:h5              （改完还能构建）
  · git status --short            （证明没越界）
"未跑"就写"未跑"，不要写成"通过"。
```

## 3. 三条最容易违反的（都是已经出过事的）

| # | 违反方式 | 已经付出的代价 |
|---|---|---|
| 1 | **不跑 `npm run type-check` 就报完成** | 上一轮 M2 就是这样：`type-check` 从未通过、**12 个类型错误**，其中 2 个是**用户可见的 bug**（管理员关闭注册后注册按钮仍然显示）。而 E2E 5/5 全绿 —— 因为没人要求跑类型检查 |
| 2 | **改了契约或手改生成物** | 前端类型会与真实接口静默不一致；`ci-web.yml` 的契约漂移检查会把这条抓出来（**这是合并进同一仓库换来的**） |
| 3 | **"看起来能跑"就当验收通过** | 前端 Agent 自己写、自己跑、自己报 `passed`，这是测试策略 §1 说的**第一道防线（与实现共谋）**。M2 到现在**没有任何 L3 独立验证** |

## 4. 谁验收（这一点比"在哪开 Agent"重要）

按 [`docs/testing/README.md`](../testing/README.md) §1 的三道防线：

| 防线 | 谁 | M2 实际做到了吗 |
|---|---|---|
| ① 实现者自带测试 | 前端 L2 | ✅ 有（5 个 E2E 用例，真实后端、无 mock，质量不错） |
| ② 独立测试 Agent | **L3，契约 + 代码，不给 ① 的测试** | ❌ **没做过** |
| ③ 对抗性验证 Agent | **L3，只要契约**（并发／绕过／越权／边界） | ❌ **没做过** |

**M1 有 L1 独立复核，M2 只有"自己写自己跑"。** 这就是为什么那两个 bug 能被 5/5 绿的 E2E 漏掉 ——
**E2E 里没有一条用例把注册模式切成 `closed`**，而"实现者想不到要测的场景"正是第 ②③ 道防线存在的理由。

> **所以派前端任务的完整动作是两次，不是一次**：先派 L2 实现，再派一个**不读 L2 测试代码**的 L3 去独立验证。

## 5. 常见误解

| 误解 | 实际 |
|---|---|
| "在 `web/` 目录开 Agent，它就只会改前端" | 目录不等于写权。**写权靠任务书 + 看板 §2，验证靠 `git status`** |
| "前端要单独一个仓库才好隔离" | 已定案合并（[`前端仓库归属对比.md`](前端仓库归属对比.md) §7）。**回滚独立性靠产物与流水线，不靠仓库数量** |
| "小程序端等弄懂上线再写" | **它上不了线**（ADR-0011 C2/C4：个人主体类目禁论坛、`request` 只允许已备案域名）。它的终点就是**在微信开发者工具里跑通**，清单见 [`../../web/小程序端人工验证.md`](../../web/小程序端人工验证.md) |
