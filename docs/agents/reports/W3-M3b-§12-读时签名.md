## 1. 背景与目标（一句话）

桶是**私有的**（匿名 GET → `403 AccessDenied ... because of bucket acl`），而 `post_image.url` 存的是**裸公网 URL**，前端直接渲染 → **M3 的验收「带图帖详情页正确展示」必然失败**。想把桶改公共读又被账号级「阻止公共访问」拦住（`403 Put public bucket acl is not allowed`，EC `0015-00000501`）。
**需求方裁决：不动安全设置，改由后端在"读"的时候签发临时 URL。** 本任务 = 读时签名（A）+ 回调响应带回结果（B）+ 回调地址不可达从静默变可见（C）。

## 2. 权威口径（**没有靠记忆实现**）

§12.3 坑 1 的判据必须来自官方实现。阿里云帮助页正文未渲染出来（抓到的纯文本里没有 `CanonicalizedResource`），于是改从 **Maven Central 取官方 SDK 的 sources jar**（`com.aliyun.oss:aliyun-sdk-oss:3.17.4:sources`），读 `OSSV1Signer` 与 `SignUtils` 原文，钉下 V1 预签名口径：

```
expires               = 过期时刻的 epoch 秒        （OSSV1Signer: expiration.getTime()/1000）
request.Header[Date]  = expires
canonicalString       = "GET\n" + "" + "\n" + "" + "\n" + expires + "\n" + CanonicalizedResource
                        （两行空的是 Content-MD5 与 Content-Type；无署名头时为空串）
CanonicalizedResource = "/{bucket}/{object}"
                        + 对**每个签名参数**（参数名字典序，以 ? / & 连接）追加 "key" 或 "key=value"
signature             = base64(hmacSHA1(accessKeySecret, canonicalString))
最终 URL              = 原 URL + OSSAccessKeyId=...&Expires=...&Signature=...
```

**两条关键确认**（决定坑 1 是否成立）：
1. `RequestParameters.SUBRESOURCE_PROCESS = "x-oss-process"` —— 缩略图参数**就是**子资源；
2. 它在 `SignParameters.SIGNED_PARAMTERS` 列表里，且 SDK 的 `buildCanonicalizedResource` 对签名参数是**带值**拼（`paramValue != null → "=" + value`）→ **必须进 CanonicalizedResource**。
   实现里把该列表**全量**抄进了 `V1OssReadUrlSigner.SIGNED_PARAMETERS`（不是只放 `x-oss-process`）：将来有人给 URL 加别的子资源（如 `response-content-type`）也会被正确纳入，而不是"悄悄漏掉 → 403"。

## 3. 任务 A/B/C 的实现

### A 读时签名（铁律 3 的落地方式）
| 位置 | 内容 |
|---|---|
| `common/oss/OssReadUrlSigner` | **接口**，`String sign(String url)`，**不持凭据**（任何模块都能依赖） |
| `media/oss/V1OssReadUrlSigner` | 实现（用 `OssCredentialProperties`），注册为 Bean |
| `post/service/PostService` | 只注入**接口**，对 `PostDetailVO.coverUrl`、`images[].url`、`images[].thumbUrl`、`PostSummaryVO.coverUrl` 现签 |

- **`post` 没有 import 任何 `media` 类**（ArchUnit 的 `ARCH_no_cross_module_dependency` 会证明这一点）。
- 有效期做配置项 `hy.oss.read-url.ttl-seconds`（默认 **3600**，§12.2 建议值）。键**不在** `application.yml` 里（该文件由 L1 维护），走代码默认值 + 环境变量覆盖。
- 三条纪律写在实现注释里：① 不要缓存签名 URL（带 `Expires`，是临时的）；② 只签本项目 OSS 目录下的 URL；③ 已签名的 URL 不二次签名。

### B CR-G：回调响应带回落库结果
- 新增 `media/vo/OssCallbackResultVO{id, url, thumbUrl}`；`registerUploadedImage` 返回它；controller 的响应带上 `data`。
- **CR-007 其余不变**：仍 HTTP 200 + 统一响应体 + **显式 `Content-Length`**（OSS 文档要求；长度仍由同一份 `ObjectMapper` 序列化同一个对象算出）。
- **`url` 返回的是裸 URL，不是签名 URL** —— 三个理由（写在 VO 注释里）：
  1. 它的用途是**发帖时作为 `images` 的取值**，最终要写进 `post_image.url`，而库里必须存裸 URL（签名 URL 会过期）；
  2. 发帖的"认领"是**按 URL 精确匹配**把 `post_id=0` 的行绑到新帖上：前端若提交签名 URL，就匹配不到回调写下的那一行 → **会多出一行孤儿图**；
  3. 展示用的签名 URL 由读接口现签（`OssReadUrlSigner`），不需要前端参与。

### C 回调地址不可达 → 可见（不是拦死）
- 新增 `media/config/OssCallbackUrlResolver`：解析优先级 **配置 `hy.oss.upload.callback-url`** > **环境变量 `OSS_CALLBACK_URL`** > `X-Forwarded-Proto/Host` > 请求自身。
- **启动时**（`ApplicationReadyEvent`）与**首次签名**各一条 WARN；环回判定含 `127.0.0.1`/`localhost`/`::1`（另把 `0.0.0.0` 一并算作"OSS 到不了"）。
- **刻意不做启动失败**（§12.5 明确要求）：测试与 CI 本来就用环回地址起应用，拦死会把它们带崩。要的是**可见**。
- `OSS_CALLBACK_URL` 别名的存在理由：那段 WARN 要告诉开发者"怎么办"，而给出的办法必须**真的能用** —— 一个名字写错的建议就是又一句"绿色的假话"。
- 解析器提供 `resetLoopbackWarningState()`（与 M1 `RateLimiter.reset` 同一性质：运维排障 + 让"只打一次"的告警可被用例稳定断言）。

### 顺带的搬迁（L1 已批准）
`post/image/ThumbnailUrls` → **`common/oss/OssThumbnailUrls`**，`PostService` 5 处调用随之改名，旧类删除。
理由：回调（media）要返回 `thumbUrl`，而 `media` 不能依赖 `post`；只有"搬到 common"与"复制一份"两条路，后者迟早分叉（现象：列表里的图和详情里的图不是同一张）。

## 4. §12.3 三条坑的处理（含**既有断言改动逐条理由**）

**坑 1（子资源与签名顺序）**：实现先解析 URL 里已有的查询参数 → 把**签名参数（含值、字典序）**拼进 CanonicalizedResource → 再算签名 → **最后**才追加签名参数（与 SDK 在算完之后才 `addParameter` 一致）。
断言：详情里 `thumbUrl` 的 `Signature` 由**测试独立重算**并逐字比对（测试里手写 SDK 口径，**不调用被测代码** —— 否则"两边一起错"就测不出来）；另断言 `thumbUrl` 仍带 `x-oss-process`。

**坑 2（语义变了 → 既有断言要跟着改）**：改成比 **base（对象地址）**，并新增 `bareUrl()` 助手。

| # | 文件:断言 | 改动 | 为什么 |
|---|---|---|---|
| 1 | `M3PostPublishTest` `data.images[0].url == image1` | → `bareUrl(...) == image1` | 对外已是签名 URL；比 base 与被测语义等价 |
| 2 | `M3PostPublishTest` `coverUrl == images[0].thumbUrl` | → 两侧都取 `bareUrl` | 同上；**且**签名含 `Expires`（epoch 秒），两次组装跨过一秒就会不同 → 整串比较会**偶发红** |
| 3 | `M3PostPublishTest` `visibleUrls containsExactly(image1,image2)` | → 先 `map(bareUrl)` | 同上（CR-006 那条"隐藏 =2、不过滤 0"的语义不变） |
| 4 | `M3PostPublishTest` `visibleUrls doesNotContain(bad)` | → 先 `map(bareUrl)` | 同上 |
| 5 | `M3PostQueryTest` `thumbUrl == coverUrl`、`images[0].url == originalUrl` | → 两侧取 `bareUrl` | 列表封面与详情缩略图必须**同一个对象地址**（不是"同一个签名字符串"） |
| 6 | `M3OssCallbackTest` `images.url containsExactly(expectedUrl)`、`coverUrl == thumb_url` | → `bareUrl` 比较 | 同上 |

**没有改实现去迁就测试**：以上改动全部是"断言的表达方式跟着语义走"，被测行为没有任何为测试让步的地方。

**坑 3（不能"看着像 OSS URL 就签"）**：按 `OssProperties.imageUrlPrefix()` 判前缀，外部 URL 原样返回、不追加签名参数；已签名 URL 不二次签名。用例里用 JDBC 塞了一行**外部 URL** 的 `post_image`，断言详情**原样返回**它。

## 10. 【2026-09-17 更新】DoD#5 实测：**签名被 OSS 接受，读图被 RAM 权限挡住**

### 10.1 三轮真实匿名 GET（同一对象 `post/2026/09/16/m3b-real-204515.png`）

| 轮次 | 原图 | 缩略图（带 `x-oss-process`） |
|---|---|---|
| 补授权**前**（我的路径 / 18080） | 403 · application/xml · **1777** 字节 | 403 · application/xml · **387** 字节 |
| 补授权**后**（我的路径 / 18080，**重新签名**） | 403 · application/xml · **1777** 字节 | 403 · application/xml · **387** 字节 |
| 补授权**后**（L1 独立脚本） | 403 · application/xml · **1777** 字节 | 403 · application/xml · **387** 字节 |

三轮**字节数逐字相同** → 三条路径拿到的是同一个响应，**授权确实还没生效**。

### 10.2 为什么可以断定"签名是对的"（两条独立理由）

原图的完整错误体带 `AccessDeniedDetail`（**它在 `HostId` 之后**，只看前 260 字符会被截掉）：

```xml
<Code>AccessDenied</Code>
<Message>You have no right to access this object because of bucket acl.</Message>
<AccessDeniedDetail>
  <PolicyType>ResourceGroupLevelIdentityBasedPolicy</PolicyType>
  <AuthPrincipalType>SubUser</AuthPrincipalType>
  <AuthPrincipalDisplayName>208112389532020531</AuthPrincipalDisplayName>
  <NoPermissionType>ImplicitDeny</NoPermissionType>
  <AuthAction>oss:GetObject</AuthAction>
</AccessDeniedDetail>
<EC>0003-00000001</EC>
```

1. **OSS 报出了 principal**（`SubUser` + 子账号 id）⇒ 它已从请求里**解析并接受了签名**。签名无效只会得到 `SignatureDoesNotMatch`；完全无签名不会有这块 detail。
2. 两处签名都用**独立脚本**按官方 SDK 口径重算过（`.tmp/m3c-verify-signature.mjs`，不调用被测代码）：原图 `Rdyri6SukZDa8gFThYGl0iK234s=`、缩略图 `lGYwFZunUaTLLMBLtbYQeXsFZIE=`，与 URL 内签名**逐字一致**；缩略图的 `CanonicalizedResource` 确实含 `x-oss-process=image/resize,m_fill,w_360,h_360/quality,q_80`（§12.3 坑 1 处理正确）。

### 10.3 结论与下一步（需需求方在控制台做）

`NoPermissionType=ImplicitDeny` + `AuthAction=oss:GetObject` ⇒ **绑在该子账号上的 RAM 策略仍不允许 `oss:GetObject`**（未保存 / 未绑到这个 principal / Resource 串不匹配，三者之一）。
建议照 [`../../ops/OSS配置清单.md`](../../ops/OSS配置清单.md) **§3.5** 先确认策略绑的是**同一个** principal（本请求显示子账号 id `208112389532020531`），再照 **§3.3**（该项目已栽过一次 ARN 串）核对 Resource 必须写成 `acs:oss:*:*:hy-forum-2026/post/*`。
补完授权后**无需任何代码改动**：重新起一次构建 → 取一次详情 → 匿名 GET 两个 URL 即可拿到 200（含 `Content-Type` 与字节数）。

### 10.4 顺带澄清（避免把方向判错）

L1 的独立脚本**没有拼错**：它的 canonical resource、string-to-sign 与官方口径一致，且它给出的字节数与我路径的**逐字相同**。
"看不到 `AccessDeniedDetail`"是**打印只截前 260 字符**造成的（detail 位于 `HostId` 之后）；另外**缩略图那条本来就没有 detail**（OSS 对带 `x-oss-process` 的请求不返回该块）—— 同一个响应的两块不对称，不是"匿名请求的特征"。

### 11.1 最终原始输出（匿名 GET，无任何认证头）

测试对象换成**真实可解码的 PNG**（900×700、1,893,390 字节，由 System.Drawing 生成并复验可解码），经本项目 `/api/oss/signature` 的签名**直传 OSS**（顺带在真实链路上用上了 CR-F 新增的 `accessKeyId` 字段），再发帖引用、取详情里的**读时签名 URL**：

```
原图              → HTTP 200 OK | Content-Type: image/png | 字节数 = 1893390
缩略图(360x360 q80) → HTTP 200 OK | Content-Type: image/png | 字节数 =  359293
缩略图 / 原图 = 19.0%      ← 「明显更小」本身就是"OSS 图片处理真的生效了"的证据
```

即：**M3 的"带图帖在详情页正确展示"这条验收，在私有桶 + 读时签名的前提下是成立的**（桶不需要改成公共读）。

### 11.2 顺带确认的两件事

- **CR-F 的 `accessKeyId` 在真实链路上是必需的**：本次直传的表单里就用了它（前端拿到它才能拼出 `OSSAccessKeyId`），否则 PostObject 表单不完整。
- 本次上传**刻意没带 `callback` 字段**：回调要经反向隧道打到 8080，而 8080 上当时跑的是**别人的实例** —— 读时签名的证据不该依赖别人的进程状态。回调链路本身已在早前的证据 #6（真实回调落库）与用例里单独验证过。

### 11.3 两个必须记下来的坑

**坑 A：`ImageDamage` 不是权限问题，是"假图"。**
先前那个测试对象 `post/2026/09/16/m3b-real-204515.png` **只有 68 字节**，是当时上传测试写的**假 PNG**。对它的缩略图请求返回：
```
HTTP 400 | ImageDamage | The image file may be damaged.
```
**判读口径（很重要，否则后来者会以为缩略图还没通）**：能收到 `ImageDamage` 说明**请求已经进到 OSS 的图片处理环节** —— 签名与权限**都通过了**（否则会是 `403` / `SignatureDoesNotMatch`，根本到不了图片处理器）。也就是说 400 与"读权限"无关，只与"那张图不是真图"有关。
**教训**：真实链路的证据必须用**真能被解码**的图片；用一个几十字节的占位文件会让"图片处理"这条链路看起来是坏的。

**坑 B（权限侧的真正根因，由 L1 定位）：策略 ARN 里的连字符是 U+2011。**
RAM 策略的 Resource 里两个连字符是 **U+2011 NON-BREAKING HYPHEN**，不是 ASCII `-` → ARN 串匹配不到任何资源 → 表现为 `ImplicitDeny`（`AuthAction=oss:GetObject`），而**看起来完全像"权限没生效"**。改成 ASCII 后立刻 200。
这与 [`../../ops/OSS配置清单.md`](../../ops/OSS配置清单.md) §3.3 记的那次"ARN 串问题"是**同一类**故障（不可见字符），建议把 U+2011 这一条补进那份清单的坑列表。
