## 2. 🔴 §14.2 ②「两个目录只有一个来源」—— 我是怎么保证的（L1 重点看的一条）

### 唯一的两个字面量

`OssProperties` 里只有两处目录字面量：

```java
private static final String DEFAULT_IMAGE_DIR = "post/";   // 沿用 M3，本就是配置项默认值
private static final String AVATAR_DIR        = "avatar/"; // §14 新增，唯一一处
```

**全项目其它任何地方都没有目录字面量。** 具体做法：

| 用途 | 取值方式 |
|---|---|
| 帖子图**允许前缀** | `OssProperties.imageUrlPrefix()` = 公网前缀 + `normalizedDir(imageDir)` |
| 头像**允许前缀** | `OssProperties.userAvatarUrlPrefix(userId)` = 公网前缀 + `userAvatarDir(userId)` |
| 头像**目录** | `OssProperties.userAvatarDir(userId)` = `normalizedDir(AVATAR_DIR) + userId + "/"` |
| 签名下发的 `dir` | 由**允许前缀反推**：`allowedPrefix.substring(publicPrefix.length())` |
| 帖子图 URL 校验（M3） | `PostService.resolveImageUrls` 用 `imageUrlPrefix()` |
| 头像 URL 校验（§14） | `ProfileService.requireOwnAvatarDirectory` 用 `userAvatarUrlPrefix(userId)` |

**关键点**：签名侧与校验侧**用的是同一对方法**，因此"签名说能传到哪"与"后端认哪个前缀"
在**构造上**不可能不一致。这不是我发明的做法 —— M3 第二交付段的 `OssSignatureService`
当时就是用"从前缀反推 dir"解决同一个问题（那是裁决 ① 的用意），本次沿用同一手法并把它
扩展到第二个目录。

**顺带收敛的一处**：目录归一化（去首尾斜杠、补尾斜杠）原来只有 `imageUrlPrefix()` 里有那段
`while (startsWith("/"))` 循环。加头像时我没有再抄一遍，而是抽成 `normalizedDir()` ——
两处各写一遍的话，迟早有一处漏判（而漏判的表现是"签名目录与校验前缀差一个斜杠"，
前端传上去、后端不认，日志无错）。

### 为什么头像目录不是配置项

`application.yml` 是 L1 独占、加键要走 CR，因此 `AVATAR_DIR` 目前是**代码默认值**
（一个常量，仍是单一来源）。我**刻意没有**为了跟 `imageDir` 对称而硬加一个配置键 ——
「为对称而加配置」会让配置面变大而收益为零。
**建议**（提请 L1 裁）：若将来需要运维改这个目录，加 `aliyun.oss.avatar-dir` 并让
`AVATAR_DIR` 变成它的默认值；在它被批准前唯一的字面量就在那一行。

## 3. 🔴 头像目录按用户隔离的落地（§14.2 ①）

- 目录 = `avatar/{userId}/`，`userId` **只来自登录态**（`CurrentUser.requireId()`），
  **不接受请求参数**。若让调用方传 `userId`，用户 A 就能拿到"往 B 的目录写"的签名 ——
  "你只能用自己目录下的对象"这条校验的**前提**当场失效。
- 前端零成本：照填签名响应里的 `dir`（§14.2 ① 原话），前端不需要知道 `userId`。
- 校验：`avatarUrl.startsWith(userAvatarUrlPrefix(我))`。
  配置缺失时前缀为空 → **拒绝一切**（与帖子图同一口径的 fail-closed）。
- `target` 非法取值 → **400，不静默回落到 post**：回落会让"前端拼错参数"表现为
  "头像传到了帖子目录"，而那个对象**永远无法通过头像归属校验** ——
  现象是"上传成功但头像设不上"，且日志里一个错都没有。

## 4. PUT 语义（§14.3）

- **覆盖、省略即清空**：显式 `.set(avatarUrl, null)` / `.set(bio, null)`，
  而不是"值非空才 set"（后者会让"清空"变成做不到的操作）。
- **不可编辑字段 → 400，不是静默忽略**。
- **只能改自己**：改的是登录态那个人，请求体里**没有** userId ——
  没有这个参数，就不存在"忘了校验越权"这种失误。

## 5. ⚠️ 两处被用例当场抓住的实现缺陷（如实记录）

### 缺陷 1：响应回显的是**更新前**的陈旧实体 —— 接口在说谎

第一版 `toProfileVO(user)` 传的是更新前 `selectById` 读出来的实体，
于是响应里是旧昵称/旧头像，**而库里其实已经改成功了**。
最恶劣的一点：它看起来像"改资料没生效"，客户端显示旧值，用户以为失败、反复重试 ——
正是本项目反复吃过的"界面在说谎"，只不过这次说谎的是**接口响应**。

修法：把刚应用的四个值显式传进 `toProfileVO`。
**不是**"再 selectById 读一次" —— 再读也不能证明写入成功，
真正的证明是 `affected rows == 1`（已加断言：0 行则 404，不静默返回成功）。

### 缺陷 2：「不可编辑字段必须 400」**连试两版都没生效**

这是本轮最值得记下来的一条 —— 因为它看起来最自然的那条路在本项目里是**无效的**：

| 版本 | 做法 | 结果 |
|---|---|---|
| 第一版 | DTO 上 `@JsonIgnoreProperties(ignoreUnknown = false)` | **无效**。Spring Boot 默认关掉 `FAIL_ON_UNKNOWN_PROPERTIES`（`application.yml` 的 `jackson` 段只有 time-zone/date-format），未知 key 在反序列化阶段就被**丢弃**，注解没机会起作用。用例红：带着 `username` 却返回 200 |
| 第二版 | 改成 `value = {...}` 显式点名 | **同样无效**。那个属性的语义是"**忽略**这些字段"，而我们恰恰要**禁止**忽略；它不产生"拒绝" |
| 正解 | 方法参数收 **`JsonNode`（原始 JSON 树）**，绑定前显式检查 | ✅ |

**为什么必须收 JsonNode**：参数声明成 DTO 的那一刻，多余的 key 就已经被丢掉了 ——
之后无论怎么检查都查不到。**这一点值得写进项目经验**：本项目里"想拒绝未知字段"
不能靠注解，只能靠"先拿原始树"。

代价（已处理）：参数改成 `JsonNode` 后 Bean Validation 不再自动触发，
因此显式 `validator.validate` 一次 —— 否则"昵称为空/超长"会漏到库里，
变成 SQL 报错的 500 而不是本该的 400。

**为什么不改成全局开启 `FAIL_ON_UNKNOWN_PROPERTIES`**：那会让**所有**接口
对"多传一个键"（哪怕是前端内部的 `_dirty`）都 400，代价落到别人头上；
而且 `application.yml` 是 L1 独占。本方案把代价限制在这一个端点的入参形状上。

## 7. ⚠️ 两处环境陷阱（本轮新发现，建议进 `docs/agents/README.md` §7.2）

### 7.1 `-Dproject.build.directory` **不生效**，所有构建共用 `server/target/`

我按习惯用 `-Dproject.build.directory=D:\demo\.m4build\<名字>` 想隔离输出，
实测**没有生效** —— 产物一律落在默认的 `server/target/`。
证据：`server/target/classes/.../UserProfileController.class` 的时间戳跟着每次构建变，
而 `.m4build\<名字>` 下根本没有 `classes` 目录。

**后果**：多次构建/变异之间**共享同一份 class**，隔离意图落空。

### 7.2 还原源码后，Maven 可能**不重编译** → 用例跑在旧字节码上（一次假红）

`Copy-Item` 还原会**保留原来的修改时间**。若还原后的源码 mtime 早于 class 文件，
Maven 的增量编译会判定"无需重编译"，于是用例跑的是**变异版的字节码** ——
表现是"代码已还原、工作区与已验证绿的提交逐字一致，却仍然红"。
我遇到过一次（随后同一条命令重跑即绿，因为那次触发了重编译）。

**规避**：还原改动后不要立刻相信结果 —— 用 `mvn clean` 或改动一下文件触发重编译再跑。
**注意**：本项目 8080 上跑着的进程**锁住了 `server/target/*.jar`**，
`mvn clean` 会失败（`Failed to delete ... .jar`）—— 这是正常现象，不是构建坏了；
此时改用"触碰源文件 + 重跑"来强制重编译。

1. **`AVATAR_DIR` 是否升为配置项**（`aliyun.oss.avatar-dir`）→ 见第 2 节末，提 L1 裁。
2. **`OssProperties.avatarDir()`** 目前只被"判别用"暴露，尚无调用方 ——
   若评审认为多余可去掉（我没有为它编造调用点）。
3. 本人看自己资料时 `isFollowing/isFollowedBy` 返回 `false`（**不是** `null`）。
   这不是另定口径：`UserService.getProfile` 在已登录时就是算
   `isFollowing(me, me)`，而 `follow` 表不允许自我关注，结果本就是 `false` —— 与既有路径逐字一致。
   `null` 在本项目里的语义是"未登录、未知"，用在这里会让前端把"我自己"渲染成未登录态。
4. §14 未做的：**契约重导**（新增 `PUT /api/user/profile` 与 `signature?target=avatar`）
