## 1. 「网站端打通」到底指什么

需求方口径：**先把网站端（H5）打通**，小程序端先搁置。

按这个口径，目标是这条链路在浏览器里能从头走到尾：

```
注册 → 登录 → 看版块 → 看帖列表 → 发一条资源帖 → 看详情 → 评论 → 点赞 → 收藏 → 个人主页
```

**后端缺口 = M3 + M4。** 这条链路上 M5（内容安全/通知）与 M6（管理后台）**不阻塞"能走通"**，
但它们阻塞"能公开" —— 因为 A5（公开 UGC 论坛的内容审核义务）与 M5/M6 的验收要求是硬合规项，
不是体验项。**先打通、后合规是可行的顺序，但必须知道 M5/M6 不能省。**

---

## 2. 为什么下一步是 M3（依赖倒推，不是按编号轮）

| 依据 | 说明 |
|---|---|
| M4 依赖 M3 | 评论挂在帖子上、点赞/收藏的对象是帖子。没有 `post` 实体，M4 无处落脚 |
| M5 依赖 M3 + M4 | M5 的验收要求"含敏感词的**帖子与评论**均进入待审"，两者都得先存在 |
| M6 依赖 M5 | 管理后台要审的是 M5 建起来的那条队列 |
| **前端全卡在这** | 前端的首页 / 版块 / 详情 / 发帖四个页面**实测全部 404**（`/api/boards`、`/api/posts`、`/api/posts/{id}` 逐个探过）。它们现在只是骨架，不发真实请求 |
| 契约增量最大 | M3 一次新增约 8 个路径，是 M1 之后契约的第一次实质扩张 |

**M3 的交付物与验收（照抄 [`PLAN.md`](../PLAN.md) §4，不重定义）**

- 交付物：版块列表、发帖、帖子列表、详情、九宫格、网盘卡片、直传签名与回调
- 验收标准：**可从零发布一条带图资源帖并在详情页正确展示与复制**

## 3. M3 的端点（来源 [`技术方案.md`](../技术方案.md) §6）

| 方法 | 路径 | 鉴权 | 备注 |
|---|---|---|---|
| GET | `/api/boards` | 否 | 版块列表（含 `isResource` 标记） |
| GET | `/api/posts` | 否 | `boardId`、`sort=latest\|hot\|essence`、`page`、`size` |
| GET | `/api/posts/{id}` | 可选 | 详情；浏览量 +1（走 Redis） |
| POST | `/api/posts` | 是 | 资源版需 `diskType`、`diskUrl`，`diskCode` 可选 |
| PUT | `/api/posts/{id}` | 是 | 仅作者，限发布后 30 分钟内。**任何内容变更后 `status` 一律回 0 重审**（防审核绕过，§8.6 第 6 条） |
| DELETE | `/api/posts/{id}` | 是 | 仅作者或管理员，逻辑删除 |
| GET | `/api/posts/search` | 否 | `keyword`，检索标题与正文 |
| GET | `/api/oss/signature` | 是 | 返回 `{host, policy, signature, dir, expire, callback}` |
| POST | `/api/oss/callback` | **OSS 回调，需验签** | 上传成功回调，验签后写 `post_image` 表 |

> 点赞 / 收藏（`POST|DELETE /api/posts/{id}/like`、`/collect`）**归 M4**，不属 M3（依据 `PLAN.md` M4 行）。

**对契约的影响**：`openapi.json` 从 **8 个路径扩到约 16 个**，新增若干 schema（`BoardVO`、`PostVO`、`PostCreateRequest`、`OssSignatureVO` 等）。
→ **这是前后端仓库归属问题第一次真正咬人的时刻**，见 §5。

## 4. 前置阻塞项：OSS 回调在本地**不可达**

这是 M3 唯一会卡死的技术点，必须先解决。

**问题的形状**：直传流程（[`技术方案.md`](../技术方案.md) §6，第 778–783 行）是

```
① 前端 GET /api/oss/signature（需登录）
② 前端直传 OSS
③ OSS 回调 POST /api/oss/callback  →  后端验签后写 post_image 表
```

第 ③ 步是 **OSS 主动请求你的后端**。本地开发时后端在 `127.0.0.1:8080` ——
**OSS 在公网上，够不到你的本机**。所以第 ③ 步在本地跑不起来，
而验收标准要求"发布一条**带图**资源帖"。

### 三条路

| 方案 | 做法 | 代价 | 判断 |
|---|---|---|---|
| **A（推荐）** | 用 `ssh -R` 反向隧道，把本地 8080 经**已有的阿里云 ECS**（`8.138.237.212`）暴露成一个公网地址，OSS 回调指向它。例：`ssh -R 8080:127.0.0.1:8080 myserver` | 隧道开着才能收回调；ECS 上要放行端口 | **契约零改动、铁律 8 零改动，本地能真的跑完整回调。** 这是唯一"不改设计就解决"的路 |
| **B** | **拆 M3 为两段**：M3a = 版块 + 发帖（**纯文本 + 网盘链接**）+ 列表 + 详情 + 搜索；M3b = 媒体（签名 + 直传 + 落库） | 验收标准要跟着拆（`PLAN.md` 要改）；"带图"这条延后 | 让"网站端打通"**不被 OSS 卡住**，代价最小；但 §4 的验收要改措辞 |
| **C** | 改流程为"前端上传成功后调后端确认接口落库"，去掉回调 | **要改 ADR-0007 与铁律 8 的形态**，得走 CR | 安全性损失很小（伪造确认只会让自己帖子里的图 404），但这属于**改已定架构**，不该由实现者顺手做 |

> **我的建议：先 A，A 不通就 B。** 不要选 C —— 回调不是多余设计，它是"前端不能伪造上传结果"的那道闸；
> 拆掉它省不了多少事，却要动一份已接受的 ADR。

### 另一个前置：OSS 本身存在吗

`PLAN.md` A1 只说"已有阿里云服务器"。**Bucket 与 AccessKey 是否已创建，文档里没有记录。**
直传需要：Bucket（地域 / 读权限 / **CORS 必须放行 H5 的源**）+ **RAM 子账号** AccessKey（只授该 Bucket 的 `PutObject`，依据 R7「最小授权」）。

## 5. 契约变更：已定，且已不再咬人

M3 让 `openapi.json` 从 8 个路径扩到约 16 个。**这个问题已于 2026-09-15 解决**：

需求方选定**方案 A（合并回本仓库，前后端两条独立流水线）**，并已用 `git subtree` 执行完毕 ——
**前端现在在 `web/`，契约回到仓库根一份**。执行记录与验证见
[`前端仓库归属对比.md`](前端仓库归属对比.md) §7.1。

因此 M3 的契约变更流程变成：

```
后端改注解 → L1 重导 openapi.json → 重新生成 web/src/api/generated/schema.d.ts
                                              ↓
                              vue-tsc --noEmit 对业务代码报错 → 前端必须跟上
```

**这才是"编译器挡住契约漂移"**（分仓库时它挡的是"快照变了"，见 [`README.md`](README.md) §1.1 的修正）。

### 5.1 仍待清理的一件遗留

`web/src/api/generated/openapi.snapshot.json` 是**合并前**为跨仓库而留的契约副本，
以及配套的 `web/scripts/check-contract.mjs`、`web/src/api/contract.ts` 里的 `OPENAPI_SNAPSHOT_SHA256` 常量。

**契约现在只有仓库根一份，这套副本机制应当退役** —— 但它不能随手删：
`check-contract.mjs` 的比对逻辑（尤其"比结构不比字节"的经验）与 `contract.ts` 里
对**形状缺口**的说明都是有用的信息。退役方案建议：

1. 生成类型的输入改为**仓库根 `openapi.json`**（`npm run gen:api` 改指向）
2. 保留"契约漂移会被 CI 挡住"这件事，但**由编译器承担**，不再需要 SHA256 常量
3. 删除快照文件；把 `contract.ts` 里关于 `captcha` / `register-mode` 形状缺口的说明
   **原样搬进 CR-005**（见 §5.2）

### 5.2 顺带要提的 CR：两个接口的形状缺口

前端实测发现 `GET /api/auth/captcha` 与 `GET /api/auth/register-mode` 在契约里
`data` 被声明为 `Record<string, any>`（`ApiResponseMapStringObject`），**具体字段名没有静态声明**。
前端为此做了「人工窄化类型 + 运行时校验」的临时层，并在注释里写明**"这是契约不足，正式做法是提 CR"**。

**CR 队列里没有这一条**（CR-001~004 都不是）。M3 改契约时应一并处理：
`captcha` → 具名 `CaptchaVO`；`register-mode` → 带取值约束的字段（`open` / `invite` / `closed`）。
**临时层必须有到期日，否则它会变成永久设施，而契约永远缺这两块。**

## 7. 需要需求方回答的三个问题

| # | 问题 | 为什么必须你答 |
|---|---|---|
| **Q-A** | **阿里云 OSS 的 Bucket 建了吗？AccessKey（RAM 子账号）有了吗？** | 没有它 M3 的"带图"验收跑不完。这是**唯一会卡死 M3 的前置** |
| **Q-B** | OSS 回调走 **A（ssh -R 隧道）** 还是 **B（拆 M3，先做纯文本帖）**？ | 它决定 M3 的验收标准要不要改，以及任务书怎么写 |
| **Q-C** | 前后端仓库归属 **A（合并回 `web/**`）** 还是 **B（保持独立 + 补机制）**？ | M3 契约要扩一倍，这个决定必须在契约冻结前落地 |

### 顺带登记：小程序端搁置的两个后果（不是问题，是事实）

1. **M2 的验收标准包含小程序端**（`PLAN.md` M2 行：② 微信小程序端在开发者工具中可完成同上）。
   既然搁置，**M2 只能记为「部分验收」**，不能标完成。已登记为交接事项 **H9**（暂挂）。
2. **「等弄懂小程序怎么部署上线，再写小程序」这个条件，在本项目里永远到不了。**
   依据 [`adr/0011`](../adr/0011-前端改用uni-app作为唯一前端.md) 的 C2 与 C4：
   - **C4**：个人主体小程序的类目**不允许「论坛 / 社区」** → 提交审核必然被拒
   - **C2**：`request` 只允许**已备案的 HTTPS 域名** → 真机与正式版都连不上本地后端
   - **C1**：个人主体不支持 `web-view` → 也不能像 APK 那样套站点

   所以**这个小程序端的终点就是「在微信开发者工具里跑通核心流程」**（这正是 M7 的验收措辞，
   也是 [`web/小程序端人工验证.md`](../../web/小程序端人工验证.md) 那份清单在做的事）。
   **"上线"不是它的前置条件，而是它做不到的事** —— 若把上线当成前置，等于永久搁置。

   > 这个矛盾需求方在 ADR-0011 时已经知情并接受。此处再写一次，是因为口径又变成了
   > "等弄懂怎么上线再写"，与当时的结论相反。
