## 5. 完成定义（DoD）—— 必须贴出真实命令输出

### 5.1 测试库基建可用
1. 能在测试里连上 `hy_forum_test`（本机 MySQL）与 `192.168.100.128:6380`（VM Redis）。
2. 贴出：`powershell -File scripts/init_test_db.ps1 -User root -Password '***'` 的输出，以及你的测试跑通后的输出。

### 5.2 幂等样板（**本任务最重要的产出**）
用 **schema 里已有的 `post_like` 表**（业务代码还没写，用 `JdbcTemplate` 或 Mapper 直接操作）写一个**并发幂等**测试，作为 M4/M5/M6 的照抄样板：

- 测试名：`SAMPLE_idempotency_concurrent_unique_index`
- 做法：**20 个线程并发**对同一 `(post_id, user_id)` 插入 `post_like`
- 断言：① 该组合**行数 = 1**；② 捕获 `DuplicateKeyException` 的线程数 = 19
- **必须提供"红 → 绿"两次输出**：先让它失败（例如断言 20），再让它通过。
  **一个从未失败过的测试不算数**（纪律见 [`../../testing/README.md`](../../testing/README.md) §2）
- **注意清理**：并发测试不能用 `@Transactional` 回滚（各线程事务相互独立），必须在 `@BeforeEach`/`@AfterEach` 显式清表或依赖每次重建。

> 为什么用 `post_like` 而不是等 M4：**样板必须在没有业务代码时就能跑通**，否则 M4 只能边写业务边试基建，样板就不成其为样板。

### 5.3 把 M0 的 CHECK 实证搬进测试套件
- 测试名：`SCHEMA_check_constraint_rejects_violation`（**双向**）
- 断言：① 合法主楼 `(0,0)` 与楼中楼 `(x,x)` **写入成功**；② 三种非法组合 `(5,0)`、`(0,7)`、`(3,9)` **必须失败**
- 目的：把 `scripts/verify_m0.ps1` 里的一次性实证变成 **CI 每次自动跑**的守护
- ⚠️ **只测拒绝是不够的**：写成 `CHECK(1=0)` 的错误约束同样能通过"拒绝测试"，却会让所有合法评论写入失败。这是 L1 在 M0 阶段真实踩过的坑。

### 5.4 CI 流水线（`.github/workflows/ci.yml`）
按 [`../../testing/README.md`](../../testing/README.md) §4 的顺序实现，至少包含：

1. 重建测试库（用 GitHub `services: mysql` + `services: redis`，**不要依赖本地 Docker**）
2. `mvn test`（含 ArchUnit）
3. **`openapi.json` 漂移检查**：重新导出并与仓库比对，不一致则失败
   > `openapi.json` 在 M1 任务产出前尚不存在 → 该步先做「文件不存在则跳过并打 warning」，并在报告中说明这是**临时状态**。
4. 覆盖率缺口脚本（见 5.5）

### 5.5 覆盖缺口检查脚本

## 7. 提示

- 本地测试库必须用 **MySQL 8.0.16+**（否则 `CHECK` 只解析不生效，5.3 会**假通过**——这是"测试骗人"的典型）。本机为 8.0.34，满足。
- 并发测试的线程数不要凭感觉：20 线程失败率过低会掩盖竞态；若第一次跑就"绿"，**先怀疑测试没真的并发**（例如在事务里串行执行了）。
- 不要引入 pitest 这类重工具。变异测试由**独立的 L3 Agent** 用"手工改坏实现"的方式做，见 [`../../testing/README.md`](../../testing/README.md) §2 纪律三。
