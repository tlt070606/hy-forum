## 3. 要验什么（**你的主清单：以 `PLAN.md` §4 M2 的验收标准逐条为准**）

下面只是**提示**，告诉你哪几类地方最可能有洞。**不许把它当清单交差** —— 你要以 §1 的来源自己列。

**特别要试着推翻这几条**（它们都有"看起来通过、其实没生效"的历史）：

1. **注册模式**：切到 `closed` 之后，注册入口是否**真的**不可用、且**给出"暂未开放注册"的提示**？
   （`open`／`invite`／`closed` 三种都要走，`invite` 要有邀请码输入框）
   ⚠️ **历史**：这里曾经有过一个**用户可见 bug** —— 类型被赋错导致
   `registerMode !== 'closed'` **恒为真**，于是"关闭注册"**实际不生效**，
   而「暂未开放注册」的提示**永远不出现**。**这个 bug 是靠类型检查抓到的，E2E 5/5 全绿也没抓到**
   （它的用例从没把注册模式切到 `closed`）。**所以：你必须真的把模式切成 `closed`。**
2. **查询失败时不许冒充业务状态**：如果 `GET /api/auth/register-mode` 拿不到（例如后端返回 500），
   页面是**明确报错**，还是**默默显示成某个模式**（那就是"拿失败当成功"）？
3. **错误码 → 文案**：验证码错 → `1003`、用户名重复 → `1001`、密码太弱 → 有明确提示。
   **不要只看"报了错"**：要看报的是**哪一个**错（错误的报错比不报错更坏）。
4. **token 携带与失效**：登录后受保护请求带 `Authorization`；**未登录/失效时**是否**跳登录页**
   （而不是白屏、死循环、或把 401 当成功）。
5. **契约一致性**：页面里出现的字段名与我们 `openapi.json` 里的**是否一致**
   （用浏览器实际发出的请求/响应来核，不要读源码）。

## 4. 交付物（**只写 `tests/verify/w4-m2/**`，不要改 `web/**` 的任何文件**）

1. **你自己写的 E2E**：`tests/verify/w4-m2/*.spec.ts`（或等价的 node 脚本）。
   用**用户看得见的文本**去定位元素；定位不到就在报告里点出来（那本身是一条发现：
   界面没有可被验证的抓手）。
2. **逐条结论表**：`tests/verify/w4-m2/报告.md`
   —— 列 `验收项 / 期望（来自哪一份文件的哪一句） / 实测 / 结论 PASS|FAIL / 证据`。
   **每条 FAIL 必须附命令输出或响应原文。**
3. **反向验证（硬要求）**：至少两条"**证明你的检查会失败**"。
   推荐：① 把前端指向一个**错误的后端地址** → 你的注册流程用例必须变红；
   ② **停掉后端**（验完再起回来，或用错误端口代替）→ 相关用例必须变红而不是静默通过。
   **一个从未失败过的检查不能证明它在检查任何东西**（[`../../testing/README.md`](../../testing/README.md) §2）。
4. **发现清单**：按严重度排。**发现"界面在骗人"（显示成功但没成功、显示状态但状态是猜的）的排最前。**

## 5. 三条硬规矩

1. **你不修任何东西。** 发现 bug 只报告。**修了就不是独立验证了** ——
   那会把你变成作者，而作者不能验证自己的东西。修是后续任务的事，由 L1 派。
2. **不许用「我看了源码，它应该是这样」当证据。** 证据只能是**命令输出、响应原文、截图**。
   推断与实测必须分开写，**不许混在一句话里**。
3. **拿不准就如实写"未能验证"并说明卡在哪** —— 这比一个含糊的 PASS 有用得多。
