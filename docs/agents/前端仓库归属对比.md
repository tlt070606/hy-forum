# 前端仓库归属：合并回本仓库，还是保持独立仓库

> **这是决策支持文档，不是决策。** 需求方要求先看对比再定。
> 触发：2026-09-15 核对发现前端工程在 `D:\demo\Hy论坛_uni-app`（**独立 git 仓库**），
> 而本仓库的看板 §2 仍把前端写作 `web/**`（且选型写着已被 ADR-0011 废掉的 Vant）。
>
> 事实部分均为 2026-09-15 实测；判断部分标注了它是判断。

### 1.1 前端是怎么保持与契约同步的（现有机制）

```
后端改注解 → 重导 openapi.json（本仓库，L1 冻结）
                    ↓  ← 这一步是【人工】的
          人工覆盖前端的 snapshot.json
                    ↓
          npm run gen:api  →  schema.d.ts
                    ↓
          npm run check:contract  →  需要【本机后端正在运行】才能比对
```

三道人工缺口：**覆盖快照要人做、检查要人跑、而且检查比对的是"结构"**（路径、方法、schema 名、版本），
**字段级改动（如某字段从必填改可选）不在比对范围内** —— 这一点前端脚本自己的输出里就写明了。

## 2. 方案 A：合并回本仓库（前端放 `web/**`）

即恢复 ADR-0011 与看板 §2 原本的设计。

### 怎么做（可执行）

```powershell
cd D:\demo\Hy论坛
# 1) 用 subtree 保留前端那 4 个提交的历史（也可直接复制 51 个文件，历史短，损失可接受）
git subtree add --prefix=web git@github.com:tlt070606/hy-forum-uni-app.git main --squash

# 2) ⚠️ 若改为直接搬整个目录，必须先删掉 web\.git
#    否则后端仓库会把 web 当成嵌套仓库/gitlink，前端文件根本不会被跟踪
```

搬完之后：

- 前端原有的 `.gitignore` 在 `web/` 下**照旧生效**（git 支持嵌套 ignore），
  所以 `web/node_modules/`、`web/dist/`、`web/.npm-cache/` 不需要在本仓库 `.gitignore` 里重写一遍。
- 前端 `.npmrc` 把 npm 缓存重定向到 `web/.npm-cache`，路径自适应，不用改。
- **前端远端 `hy-forum-uni-app` 必须归档或删除。** 否则会有两个可推的地方，比现在更糟。

### 得到什么

| 收益 | 为什么这条重要 |
|---|---|
| **契约回到一个文件** | 不再需要「快照 + SHA256 常量 + 靠本机后端比对」这套替代品 |
| **"契约漂移被编译器挡住" 才真正成立** | `schema.d.ts` 从仓库根的 `openapi.json` 生成；契约一变，`vue-tsc --noEmit` 立刻对业务代码报错 |
| 一个 CI 里能同时管两边 | 后端 job 与前端 job 并行；可加一条 `npm run gen:api` 后 `git diff --exit-code` 来挡"改了注解忘了重生成类型" |
| 看板 §2 的所有权表**重新有意义** | L1 独占 `web/src/api/generated/**` 这条规矩终于能执行 |
| 不需要任何新凭据 | 不引入 PAT |
| 「前端 L2 禁止读 `server/src/main/java/**`」能落地 | 前端 Agent 在同一个仓库里，能读 `docs/agents/` 的广播与 CR 队列 |

### 要付什么

| 成本 | 说明 |
|---|---|
| 一次性搬迁 | 约 10 分钟（subtree + 推送）。历史只有 4 个提交，损失也小 |
| **必须同时处理前端远端** | 否则出现两个真相源，这是"比现在更糟"的唯一路径 |
| CI 配置变复杂 | 一个 workflow 里两种语言两种缓存；Node 版本要与本机对齐（**本机 v26.4.0**，GitHub `setup-node` 支持到哪个大版本需现场确认） |
| 仓库体量感受变差 | 仓库本身不变大（`node_modules`/`dist` 都不跟踪），但 `git status` 会多出一个子树 |
| **写权隔离从"物理"变成"约定"** | 见下面 §4 的反面论证 |

## 3. 方案 B：保持独立仓库，把缺的机制补上

### 要补的三件事（缺一件就等于没补）

1. **前端仓库加 CI**（现在完全没有）
   ```yaml
   # hy-forum-uni-app/.github/workflows/ci.yml（新建）
   - npm ci
   - npm run type-check          # vue-tsc --noEmit
   - node scripts/check-contract-offline.mjs   # 与后端 openapi.json 比对（见第 2 条）
   ```
2. **把契约比对从"要本机后端"改成"离线比对"**
   现在的 `check-contract.mjs` 要求 `http://127.0.0.1:8080` **正在运行** —— 这个前提在 CI 里不成立。
   改成拉取后端仓库的 `openapi.json` 再比。**这需要一个 fine-grained PAT**（`Contents: read` on `hy-forum`）
   放进 GitHub Secrets（**不能进仓库** —— 铁律 5）。
   同时应把比对口径从"只比结构"升级为"逐字段比对（去掉 `servers`）"，否则字段级漂移仍然漏网。
3. **写清跨仓库的 CR 跑腿方式**
   前端发现契约不足 → 提给谁、谁改 `openapi.json`、谁重新生成快照。
   而且 **L1 必须同时持有两个工作目录**，否则它没法一次改完两侧。

### 得到什么

| 收益 | 说明 |
|---|---|
| 不动现有结构 | 零搬迁风险；前端的 `.npmrc` 沙箱适配、Playwright 配置、已跑通的 E2E 都不受影响 |
| 写权隔离是**物理的** | 前端 Agent 的工作目录就只有前端仓库，它**不可能**越界写后端 —— 这是文件系统保证，不是表格保证 |
| 两端可独立构建/发布 | 后端改一次 docs 不会触发前端构建 |

### 要付什么

| 成本 | 说明 |
|---|---|
| **契约永远是两份** | 这个项目已经为"同一事实存两份"付过两次代价：`技术方案.md` §13–§15 的副本漂移了 6 处；看板 §2 今天还写着空气一样的 `web/**` |
| 引入一个 PAT | 多一个要维护、要轮换的凭据 |
| E2E 无法进 CI | 它需要一个活着的后端（JDK + MySQL + Redis + 打包 + 启动）。放 CI 里要先解决"CI 怎么拿到后端代码"，成本与上面的 PAT 问题重复 |
| 跨仓库 CR 靠人跑腿 | 每次契约变更都要人同步两侧 |
| 编译器保证退化 | `vue-tsc` 挡的是"**快照**变了"而不是"**契约**变了" |

### 3.1 方案 C（B 的加强版，一并列出）

后端 CI 在 `openapi.json` 发生变化时，**自动向前端仓库开一个更新快照的 PR**（用 PAT + `peter-evans/create-pull-request` 之类）。
- 好处：不需要人记得同步。
- 代价：多一个自动化 + 同一个 PAT + 前端 CI 仍要自己一套；复杂度高于 A，而收益（契约一致）A 用一个文件就拿到了。
- **判断：除非有很强的理由必须分仓库，否则 C 不如 A。**

## 4. 关键判据：为什么"编译期挡漂移"只在同仓库成立

我在 [`README.md`](README.md) §1.1 里给"何时可以把前后端交给同一个 Agent"设的条件之一是
**"前后端之间已有编译器级契约校验"**。写的时候我不知道前端是独立仓库 —— 现在必须修正这个说法：

> **分仓库时，前端类型是从「快照」生成的，而快照靠人手覆盖。
> 所以 `vue-tsc` 挡住的是「快照变了」，不是「契约变了」。**
> 前端 Agent 自己也确认了这一点：它把 `OPENAPI_SNAPSHOT_SHA256` 描述为
> "**信息性常量，未参与自动化校验**"。

要让它真的成立，只有两条路：**同仓库**（A），或者**把快照同步自动化**（C）。

### 反面论证（我不掩饰）

分仓库有一个真实优点：**写权隔离是物理的**。合并之后，"前端 Agent 不许写 `server/**`"就退回成
看板 §2 表格 + `git status` 事后核对 —— 会被人违反的那种。

但要注意：**这个优点不是"分仓库"独有的** —— 它就是"一个 Agent 会话只有一个工作目录"。
而且它的代价是**契约被复制了一份**，而这个项目的第一原则（铁律 1）恰恰认为
"同一事实存两份"是最贵的那类错误。

## 5. 我的建议

**倾向方案 A（合并回 `web/**`），前提是能在同一次操作里归档前端远端仓库。**

一句话理由：**契约是这个项目最贵的一份事实，不适合再复制一次。**
A 用一个文件就拿到了 B 要三套机制（CI + PAT + 离线比对）才能逼近的效果，
而且 A 让看板 §2、所有权表、CR 队列、§1.1 的规矩**全部重新生效** —— 那些文档现在有一半是落空的。

**如果你更在意"前端 Agent 物理上写不到后端"，那 B 是对的选择**，但请连 §3 的三件事一起做 ——
只保持现状（分仓库 + 无 CI + 人工同步）是**所有选项里最差的一档**，因为它的代价全付了，机制一个没建。

### 7.1 执行记录（2026-09-15）

需求方的原话理由与我的答复：

> **需求方**：「前后端你总不能放在同一个仓库里吧。他要回滚的话，前端滚前端的，后端滚后端的。」
>
> **L1**：「前后端分离」是**通信方式**（前端 HTTP 调后端、各自独立构建部署），**不是文件夹在哪**；
> 而**回滚独立性由「产物 + 发布流程」决定，不由仓库数量决定**。
> 这个项目里，前端产物是一个静态目录、后端产物是一个 jar，回滚各自换回上一版即可 ——
> **两种布局下完全一样**，合并后回滚前端时后端 jar 一个字节都不动。
> 再加 GitHub Actions 的 `paths:` 过滤（改 `web/**` 只跑前端 job，改 `server/**` 只跑后端 job），
> 独立流水线天然成立。**仓库布局真正只决定一件事：契约文件能不能被共享。**

执行命令与结果（实测，非推断）：

```powershell

# → Added dir 'web'
```

**踩到的两个坑（都已处理）**：

1. **`.gitignore` 冲突**：本仓库的 `.gitignore` 有 `.env` / `.env.*`，会在**任意深度**匹配，
   会盖掉 `web/.env`、`web/.env.development`、`web/.env.production`（前端这三个**不含凭据**、
   只有后端地址，必须入库）。已在 `.gitignore` 补三行否定规则，并写明规矩：
   **真东西放 `.env.local` / `.env.*.local`**（那几个仍被忽略）。否定规则必须排在忽略规则之后。
2. **旧目录无法改名**：`D:\demo\Hy论坛_uni-app` 被进程占用（`idea64` / `codex` / 若干 `node`），
   改名报 `being used by another process`。**内容已全部并入 `web/`，此目录可手动删除。**
