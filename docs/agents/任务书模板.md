## 5.5 提问的边界与进度心跳（**2026-09-16 新增，因为是踩出来的**）

### 5.5.1 只有三类事允许"停下等人"

**只有这三类**：
1. 要改**契约**（`openapi.json`、`docs/db/schema.sql`）；
2. 要改**铁律 / ADR**（例如绕过 OSS 直传、引入被禁的重组件）；
3. 要动**别人写权清单里的文件**。

其余一切 —— 包括"这个字段是秒还是毫秒""失败返回 400 还是 403""回调响应体长什么样" ——
**都写成"我采用的读法 + 理由"，然后继续做**，并把它作为一条 **CR 条目**留在进度心跳里与最终报告里，
由 L1 **事后**审。L1 不认可时返工一处即可；而**停下等人**的代价是一小时起步。

> **为什么改这条**：2026-09-16，一个 agent 按旧规矩停下来提了 6 个问题，
> 问题界面等人工回答 —— **等了 52 分钟**，会话期间零产出，而系统状态一直显示 `running`，
> 从外面看像"很慢"而不是"在等人"。**没有任何超时、没有任何告警。**
> 若需求方不看那一眼，它会一直等下去。
>
> 结论：**"等"必须是例外，不能是默认路径。** 探索期往前走的风险（改一处）远小于停住的风险（停一小时）。

### 5.5.2 进度心跳（**硬要求**）

任务书必须要求 agent **每轮结束（或每 ~20 步）往固定文件追加一行**：

```
.tmp/progress-<agent-id或任务号>.md
例：2026-09-16 20:40 | 正在写 media/OssSignatureService | 下一步：回调 controller | 待裁：无
例：2026-09-16 20:55 | 卡在验签公钥下载超时 | 下一步：加重试+白名单 | 待裁：CR —— 缓存时长取多少
```

- **为什么值得**：一行 append 的成本，换来"外面随时能看见它在干什么"。
  否则唯一的观察手段是**解会话存档**（zstd 多帧）或等它交付 —— 两者都是事后。
- **它同时是一个可检测的卡死信号**：心跳超过约定时长（建议 15 分钟）没更新 = 真的卡了 → L1 立刻介入。
- **L1 的巡检规矩**：派活后每 ~10 分钟看一眼心跳文件的 mtime，**不要等结束通知**。
  只看"有没有落盘"会误判（在等人与在思考从外面看是一样的）。

## 填写规则（比模板本身重要）

1. **不要复述契约数值。** 写"参数见 `ops/deployment.md` §2"，不要写"Xmx1g"。
   复述一次就多一份会漂移的副本 —— 项目已经吃过这个亏（`技术方案.md` §13–§15 漂移 6 处）。
2. **DoD 必须是可执行的命令 + 期望输出。** "实现幂等"不是 DoD，"20 线程并发点赞后
   `SELECT COUNT(*) FROM post_like WHERE post_id=1` 返回 1" 才是。
3. **必须要求"红→绿"两次输出。** 一个从未失败过的测试，不能证明它在测任何东西。
4. **必读清单要给到行号级别**（如"§4 的 M4 行"）。给范围太大会让 agent 只读一部分。
5. **一次一个模块。** 一个 agent 做 3 个模块 = 会为省事而简化，且出问题无法定位。
6. **凡是 L1 已经知道答案的对外口径，直接写进任务书，不要让 agent 来问。**
   2026-09-16 的教训：任务书在 §边界里**列出了那几类问题**（回调响应体、失败状态码、
   单位、尾斜杠），却要求 agent 来问 L1 —— 于是 6 个问题卡了 52 分钟。
   **列出问题 ≠ 回答了问题。**
7. **观察手段也要给全。** 只给环境拓扑不够，要给"怎么戳它"的具体命令
   （例：读 VM 里 Redis 的 key，与其让 agent 手写 103 行 RESP 客户端，
   不如给一行 `ssh roott@192.168.100.128 "docker exec hy-redis redis-cli -p 6380 GET <key>"`）。
8. **节奏约束**：写明单轮上限（≈70 步 / 单次工具调用 ≈10 分钟）与"到线就交付一次可见产出"。
   否则 agent 会跑出 127 步 / 45 分钟工具时间的单轮，外面看着像卡死。

## 已填示例：M4 互动模块（后端）

```markdown
# 任务：M4 评论 + 点赞 + 收藏 + 关注（后端实现）

## 0. 你的角色与身份
- 角色：L2 模块实现者
- 影响范围：`server/**/interaction/**`
- 上下文说明：你看不到派活方的对话历史。所有约束在下面的「必读」里，不要去猜。

## 1. 必读
- `AGENTS.md` 铁律 3（禁跨模块调用）、5（禁硬编码密钥）
- `docs/PLAN.md` §4 的 M4 行 ← 验收标准
- `docs/技术方案.md` §6.6（评论，含两层约束）、§6.7（关注）、§8.1（点赞与收藏幂等）、§8.2（计数一致性）
- `docs/db/schema.sql` 表 5/6/7/8/15（comment、post_like、comment_like、follow、post_collect）
- `openapi.json`：`/api/posts/{id}/comments`、`/api/comments/**`、`/api/posts/{id}/like`、
  `/api/posts/{id}/collect`、`/api/follow/{userId}`、`/api/feed`
- `docs/testing/验收项-测试映射.md` 中 M4 段全部条目

## 2. 允许修改
- `server/**/interaction/**`

## 3. 禁止
- 改 `schema.sql` / `openapi.json` / `web/src/api/generated/**`（走 CR）
- 调用其他模块的 Mapper/Service（铁律 3）
- 自己新增表或字段来"顺手解决"问题

## 4. 完成定义（贴真实输出）
1. `mvn -q test` 全绿
2. **红→绿**：先贴 `M4_like_idempotent_concurrent` 失败的输出，再贴通过的输出
3. `M4_like_idempotent_concurrent`：20 线程并发点赞同一帖 → `post_like` 行数=1 且 `like_count`=1
4. `M4_collect_idempotent_concurrent`：同上，作用于 `post_collect` 与 `collect_count`
5. `M4_collect_list_matches_count`：随机收藏/取消 100 次后，收藏列表长度 == `collect_count`
6. `M4_follow_idempotent`：重复关注同一用户 → `follow` 行数=1、双方计数各 +1 一次
7. `M4_comment_no_third_level`：对楼中楼再回复 → 不产生非法 `parent_id`/`root_id` 组合
8. `M4_counters_consistent_after_random_ops`：随机增删后跑校准任务 → 计数与关系表一致
9. **另需手工核对（并在报告中说明）**：技术方案 §6.6 的「归并到 root_id」具体落到
   哪个字段值。若文档里无法确定（当前 P1-3 未结），**报告 BLOCKED，不要自行决定**。

## 5. 契约不足时
报告 `BLOCKED` + 缺什么 + 建议变更 + 影响范围。
```

> **注意最后一条**：示例里特意留了一个"文档还没定"的点（P1-3 楼中楼语义），
> 目的是让 agent **停下来报告而不是自由发挥**。这正是 [`README.md`](README.md) §2
> 第 4 条反模式的实操方式：**不确定的地方必须在文档里写清，写不清就会变成 agent 的自由发挥。**
