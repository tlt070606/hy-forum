# AI 协作规范

> 本文件是**多 Agent 协作的唯一依据**。派活、接活、验收前必须先读它。
> 与 [`AGENTS.md`](../../AGENTS.md) 的关系：`AGENTS.md` 规定**做什么不能违反**（铁律），本文件规定**怎么分工**。
> 与 [`../PLAN.md`](../PLAN.md) 的关系：PLAN 的 M0–M8 是**里程碑与验收标准的唯一来源**；本文件的 Wave 只是**编排单位**，**不得另立验收标准**，只能引用 M 编号。

---

## 0. 为什么需要分层

项目已冻结的约束（铁律、schema、接口契约）是**单写者资源**：

- `docs/db/schema.sql`、`openapi.json` 一旦被两个 agent 同时改，必然互相覆盖；
- 契约一旦在某个 agent 手里"顺手改一下"，其他 agent 就会基于旧契约继续开发，**漂移无法察觉**。

项目已经在文档层面吃过一次这个亏（`技术方案.md` §13–§15 重复 PLAN，漂移 6 处）。所以分层的唯一目的是：**让契约只有一个写者，并让所有变更可追溯。**

## 1. 四层角色

### L0　人类（需求方 / 决策者）

| | |
|---|---|
| **只做** | 定需求；**批准契约变更**；按命令输出验收；处理 agent 干不了的（备案、账号、付费、买服务器） |
| **不做** | 逐行审代码（会变瓶颈，且看不出并发类问题） |
| **纪律** | **只认命令输出，不认汇报文字。** 没有输出证据的"完成"，不算完成 |

### L1　主 Agent（契约守护者 + 集成者，每波 1 个，串行独占）

| | |
|---|---|
| **允许改** | `docs/db/schema.sql`、`openapi.json`、CI 配置、黄金路径脚本、`docs/agents/工作计划.md`（裁决与广播区）、任务书 |
| **禁止** | **写业务模块实现**（那是 L2 的活）。一旦 L1 开始写业务代码，就没人守契约了 —— 这是本角色最常见的失败方式 |
| **产出** | ① 每个 L2 一份任务书 ② 契约当前版本（附 hash） ③ 验收报告（每条 DoD 的命令与真实输出） |

### L2　副 Agent（模块实现者，2–4 个并行）

| | |
|---|---|
| **范围** | 一个模块 = 一个 package（或一个前端路由域） = 一个 agent |
| **允许改** | 仅任务书指定的路径（见 [`工作计划.md`](工作计划.md) §2 的所有权表） |
| **禁止** | 改契约；改其他模块的文件；与其他 L2 私下达成本文档未记录的约定 |
| **发现契约不足时** | **停下来**，在 [`工作计划.md`](工作计划.md) §3 提交变更请求（CR），等 L1 裁决 |
| **产出** | 代码 + 单元测试 + **测试"红→绿"两次命令输出** + 自评「哪些没做到、哪些没验证」 |

### L3　专用 Agent（短命、按需）

| 角色 | 给它什么 | 抓什么 |
|---|---|---|
| 测试生成 | 契约 + 代码，**不给 L2 写的测试** | 接口行为、业务不变量 |
| 对抗性验证 | **只要契约**（甚至不给实现） | 并发、绕过、越权、状态机漏洞、边界 |
| 审计（用 workflow 扇出） | 全库 | 「所有 Controller 是否都做了归属校验」「有无硬编码密钥」等铁律检查 |

### 1.1 前后端必须是两个 Agent —— 以及前端 L2 的一条硬限制

§4 的 W2 把 `M2+（前端）` 与 M3/M4/M5 并排，即**前端本来就是一个独立的 L2**，不是某个后端 L2 的延伸。
这不是排版巧合，是必须坚持的设计。理由三条：

1. **前后端之间唯一需要对的东西是文件，不是人。** 接触面就是 `openapi.json`。让同一个 Agent 管两边，
   不会让契约更一致，只会让一致性依赖**这个 Agent 记得住**。分开之后前端只有文件可看，
   契约的歧义被迫变成一次 CR —— **这正是 L1 存在的理由**。
2. **统一管理的失败方式是隐式假设。** 实例：`openapi.json` 的 `servers[0].url` 里带着**监听端口**，
   而 CI 把应用起在 18080、仓库文件是 8080（这个坑 2026-09-15 真的让 CI 红过）。
   一个"知道前后端都跑 8080"的全栈 Agent 会把这个假设**同时写进两边**，谁也不会去核对文件；
   分开时前端照文件走，第一次生成类型就会撞上它。
   **共用一份记忆的地方，就是没人核对的地方。**
3. **上下文装不下。** 后端已 51 个 main 文件 + 13 个测试类，前端是 uni-app 三端（H5 + 安卓 + 小程序）。
   这不是"能不能做"的问题，是"做得越久越糊"的问题 —— 而契约与铁律恰恰是糊了之后最先丢的东西。

**因此对前端 L2 加一条硬限制（本节最重要的一条）：**

> **前端 L2 禁止读 `server/src/main/java/**`。**
> 只允许消费 [`openapi.json`](../../openapi.json)、[`../技术方案.md`](../技术方案.md) §6／§6.1、
> [`../db/schema.sql`](../db/schema.sql)，以及自己的任务书。
> 也不得与后端 L2 直接通信（§2 反模式 4：跨模块协商必须经 L1）。

这一条与 [`../testing/README.md`](../testing/README.md) §1「**②③ 不得读取 ① 的测试代码**」**完全同源**：
给它实现，它就会去读代码"猜"契约的意图，于是契约的歧义永远暴露不出来；只给契约，它被迫提问，
而每个提问都是一次契约审查。**分离的全部收益都来自这一条 —— 不写它，分成两个 Agent 只是把一次错误变成两次。**

**代价（承认）**：交接成本真实存在 —— [`工作计划.md`](工作计划.md) §6.5 的 H1–H8 就是这么攒下来的。
但**这份成本不该由 L0 承担**：[`工作计划.md`](工作计划.md) §4 广播区与 §3 CR 队列就是为此存在。
若发现人类在两个对话之间当传话筒，那是机制没生效，不是"分开"的错。

**什么时候才该合成一个 Agent**：项目小到"一个 Agent 的上下文能同时装下契约与两边实现"，
**且**前后端之间已有编译器级契约校验（类型从 `openapi.json` 生成，契约一变前端就编译报错）。
两个条件本项目现在都不满足。**M2 建成类型生成之后仍建议保持分开** —— 那道校验是安全带，不是替代品：
它只能挡住"契约改了前端没跟上"，挡不住"契约本身有歧义"（那恰恰是前端 Agent 读不到实现才提得出来的问题）。

## 2. 四条反模式（会用错的地方）

1. **不要超过 3 层。** 不要设"副主 Agent"。每多一层转述就多丢一次约束，而丢掉的往往是铁律。
2. **L1 不转述需求，只给指针。** 任务书写「必读 `PLAN.md` §4 的 M4 行」，不要抄一遍 M4。**抄一遍就是新造一份会漂移的副本。**
3. **并行度 = 你的验收带宽，不是 agent 数量。** 3–4 个是上限；7 个并行等于 7 份待验收输出，人类立刻成为瓶颈。
4. **跨模块协商必须经 L1。** L2 之间私下约定（"你把字段名改成 x 我就好用了"）不在文档里，下次必然漂移。

## 3. 交接协议（每个 Agent 必须遵守）

```
① 开工前：读 docs/agents/工作计划.md（看广播区与所有权表）
         读自己的任务书 → 按任务书的「必读」清单去读 docs/ 与契约
② 开工时：在 工作计划.md §5 登记自己占用的范围（领取所有权）
③ 过程中：发现契约不足 → 不要改契约，去 §3 提 CR，停下等裁决
④ 结束时：在 §5 登记「改了哪些文件 + 验收输出指针 + 未完成项」
         交还所有权
⑤ L1 验收：只看 ①②③④ 是否齐、输出是否真实；不看"我觉得做完了"
```

## 4. Wave 编排（只引用 M 编号，不重定义验收标准）

| Wave | 串行/并行 | 内容 | 依赖 |
|---|---|---|---|
| **W0** | 串行 1 个 | 定 P1-3 / P1-4 → 改文档与 schema → 执行 **M0**（真 MySQL 跑 `schema.sql`、写 `seed.sql`、产出验证脚本） | 无 |
| **W1** | 串行 1 个 | **M1** 后端骨架 + 认证 + 导出 `openapi.json`；**同时建测试基建**（Testcontainers + 幂等样板 + CI 骨架） | W0 |
| **W2** | 并行 3–4 个 | **M3**（版块/帖子/OSS）、**M4**（评论/点赞/收藏/关注）、**M5**（内容安全/举报/通知）、**M2+**（前端骨架与认证） | **W1 的 `openapi.json` 已冻结** |
| **W3** | 并行 | **M6**（管理后台前端）、**M7**（安卓壳）、对抗性验证 | W2（M6/M7 可与 W2 部分重叠） |
| **W4** | 串行 | 集成 + 黄金路径全跑 + 准生产演练 | W2/W3 |
| — | 待定 | **M8** 上线 —— 卡在 `PLAN.md` §6 Q4（目标规格未定）；当前目标是**本地可用版**，M8 暂不启动 | — |

> **关键规则**：前端（M2+）**不必等后端完成**，只需等**契约冻结**。这是最容易浪费并行窗口的地方。

## 5. 上下文与角色载体

- **L1 可以每波换一个新的会话**：以 `docs/` 与 [`工作计划.md`](工作计划.md) 为长期记忆，不依赖对话历史。这样上下文永远干净。
- **L2 一律用「不继承对话上下文」的子 agent**（本项目对应 `subagent`）。这不是缺陷而是优点：

  > **子 agent 看不到我们的对话，它只能读 `docs/`。**
  > 因此 **文档写不清的地方，就是 agent 会自由发挥的地方。**

  派活时第一反应不该是「写更长的提示词」，而应是「**回文档里把它写清楚**」。

- **需要继承本会话上下文的场景**（如"审查我刚刚做的改动"）：用 `subagent_fork`。
- **`workflow`**：只用于跨大量文件的扇出（审计、迁移、批量检查），**不要**用于序列化开发（它有阶段屏障，不适合边写边联调）。
- **`ralph`**：本项目**不使用**。它适合"陌生 agent 反复试错收敛"，而本项目需要契约一致性，反复重启的陌生 agent 是契约漂移的来源。

## 6. 与项目铁律的衔接

| 铁律 | 在协作层面如何落地 |
|---|---|
| 1 文档先行 | 契约变更必须先改 `schema.sql`／`openapi.json`，再改代码；L1 是唯一执行者 |
| 2 零代码分叉 | 单一份配置（见 [`../adr/0010`](../adr/0010-部署以本地开发为基准并取消档位.md)），无环境相关分支 |
| 3 禁止跨模块调用 | ArchUnit 自动检查；任务书里逐条写明「禁止调用其他模块的 Mapper/Service」 |
| 4 禁止跨模块建表改表 | 走 [`../db/README.md`](../db/README.md) 冻结流程：改 schema → 变更登记 → 迁移脚本；**只有 L1 能改** |
| 5 禁止硬编码密钥 | 审计 agent 扇出扫描 + CI 检查 |
| 7 禁止重组件 | ArchUnit／依赖检查（禁 ES / MQ / 注册中心客户端） |
| 8 OSS 服务端签名直传 | 任务书里写明；审计项检查代码中是否出现 AccessKey |

> 铁律 6（禁止在服务器上构建）：**CI 跑在 GitHub 的机器上，不是项目服务器**，因此 CI 不违反铁律 6，而且铁律本身就建议 CI。

## 7. 工程约定（已踩过的坑，务必遵守）

### 7.1 脚本文件必须保存为 UTF-8 with BOM

本机只有 **Windows PowerShell 5.1**（`pwsh` 7 **未安装**），系统 ANSI 代码页为 **936 (GBK)**。
PowerShell 5.1 会把**没有 BOM** 的 `.ps1` 按 GBK 解读 → 中文乱码 **且解析失败**
（实测：无 BOM 时 `verify_m0.ps1` 报 **19 处语法错误，脚本根本跑不起来**；加 BOM 后 0 错误）。

| 文件类型 | BOM | 原因 |
|---|---|---|
| `.ps1` | **必须带 UTF-8 BOM** | 5.1 在 GBK 代码页下按 ANSI 解读无 BOM 文件 |
| `.sql`、`.md` | **不要带 BOM** | `mysql` 客户端不期望 BOM；markdown 无 BOM 更通用 |

> ⚠️ **实测陷阱（2026-09-14 踩过）**：用文件写入/编辑工具修改 `.ps1` 之后，**BOM 会丢失**
> （工具按 UTF-8 无 BOM 落盘）。改完必须补回，否则脚本下次执行直接乱码失败：
>
> ```powershell
> $p = '脚本路径.ps1'
> $t = [System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)
> [System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($true)))
> # 验证：0 表示能被 5.1 正确解析
> $errs = $null
> [System.Management.Automation.Language.Parser]::ParseFile($p, [ref]$null, [ref]$errs) | Out-Null
> $errs.Count
> ```

同时：**不要用 `Get-Content ... | mysql` 的方式喂 SQL 文件**（PowerShell 管道会改变文本编码，
中文种子数据会写坏），必须用 `mysql ... < file` 做**字节级重定向**。

> 命令入口也要注意：本机没有 `pwsh`，脚本一律用 **`powershell -File <脚本>`** 调用。

### 7.2 本机环境事实

| 项 | 事实 | 影响 |
