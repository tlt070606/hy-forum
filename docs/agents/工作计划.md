# 工作计划（多 Agent 协作看板）

> **本文件回答一个问题：现在谁在动哪些文件、谁想改契约、有什么新决定要广播。**
> 使用规则见 [`README.md`](README.md)（AI 协作规范）。

---

## 0. 红线与写权

**红线：本文件只登记「协作状态」，绝不复制契约内容。**
不得把表结构、接口字段、参数数值抄进来 —— 一旦抄进来，它就成了第 3 份事实来源，必然漂移（本项目已在 `技术方案.md` §13–§15 吃过一次）。
契约永远只在 `docs/db/schema.sql` 与 `openapi.json` 里，本文件只写**指针**。

| 区段 | 写权 | 读权 |
|---|---|---|
| §1 当前状态 | **仅 L1** | 所有人 |
| §2 文件所有权 | **仅 L1** | 所有人 |
| §3 变更请求队列 | **仅 L1**（L2/L3 通过汇报提交 CR） | 所有人 |
| §4 广播区 | **仅 L1** | **所有 Agent 每次开工必读** |
| §5 Agent 登记 | **仅 L1** | 所有人 |

**为什么 L2/L3 不直接写本文件**：多个 Agent 同时写同一文件会互相覆盖（文件级写入）。让 L1 做唯一写者，冲突就从根本上消失了 —— 这也是 L1「集成者」角色的实质内容。

> L2/L3 的产出通过**任务汇报**回到 L1，由 L1 登记进本文件。
> 若将来出现必须由 L2 直写的场景，改为 `docs/agents/log/<agent-id>.md`（一 Agent 一文件），本文件只放链接。

## 3. 变更请求队列（CR）

**什么时候用**：L2/L3 发现契约（表结构 / 接口字段 / 错误码）不足以完成任务时。

**流程（不要跳步）**：

```
L2 发现契约不足
  └─ 不改契约、不绕过 → 结束本轮并报告 "BLOCKED + CR 内容"
      └─ L1 裁决（批准 / 拒绝 / 改方案）
          └─ 批准：L1 改契约 → 本区登记 → §4 广播 → 用 send_message 让原 L2 继续
              └─ 其他在跑的 L2：下一轮交互时由 L1 告知，或自行读 §4 发现
```

**禁止**：L2 自己加字段、自己改 `openapi.json`、用"我这边先这么写，回头对齐"的方式绕过。

### 6.5.1 两条值得固化的工程做法（M1 产出，建议后续模块照抄）

- **`ARCH_no_heavy_components` 解析 Maven 解析后的依赖树**（`target/dependency-tree.txt`，由 `maven-dependency-plugin` 在 `process-test-classes` 生成；读不到就调 `mvn dependency:tree` 兜底），**不扫本地仓库目录** —— 后者会把**别的项目**下载的组件算成自己的，是典型假阳性。
- **`ARCH_no_cross_module_dependency` 有"防假绿"前置断言**：若七个业务包在编译产物里压根不存在，包依赖规则会**空转通过**。因此每个包都放了 `PackageMarker` 并**断言其存在**，规则才真的在检查东西。

> 这两条属于"让测试不骗人"的设计，与 [`../testing/README.md`](../testing/README.md) §5.1 的两条坑同源。**后续写架构测试的人请照抄这个思路：先证明规则真的在跑，再相信它的绿。**
