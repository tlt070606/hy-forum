## 0. 红线与写权

**红线：本文件只登记「协作状态」，绝不复制契约内容。**
不得把表结构、接口字段、参数数值抄进来 —— 一旦抄进来，它就成了第 3 份事实来源，必然漂移（本项目已在 `技术方案.md` §13–§15 吃过一次）。
契约永远只在 `docs/db/schema.sql` 与 `openapi.json` 里，本文件只写**指针**。

| 区段 | 写权 | 读权 |
|---|---|---|
| §1 当前状态 | **仅 L1** | 所有人 |
| §2 文件所有权 | **仅 L1** | 所有人 |
| §3 变更请求队列 | **仅 L1**（L2/L3 通过汇报提交 CR） | 所有人 |
| §4 广播区 | **仅 L1** | **所有 Agent 每次开工必读** |
| §5 Agent 登记 | **仅 L1** | 所有人 |

**为什么 L2/L3 不直接写本文件**：多个 Agent 同时写同一文件会互相覆盖（文件级写入）。让 L1 做唯一写者，冲突就从根本上消失了 —— 这也是 L1「集成者」角色的实质内容。

> L2/L3 的产出通过**任务汇报**回到 L1，由 L1 登记进本文件。
> 若将来出现必须由 L2 直写的场景，改为 `docs/agents/log/<agent-id>.md`（一 Agent 一文件），本文件只放链接。

## 3. 变更请求队列（CR）

**什么时候用**：L2/L3 发现契约（表结构 / 接口字段 / 错误码）不足以完成任务时。

**流程（不要跳步）**：

```
L2 发现契约不足
  └─ 不改契约、不绕过 → 结束本轮并报告 "BLOCKED + CR 内容"
      └─ L1 裁决（批准 / 拒绝 / 改方案）
          └─ 批准：L1 改契约 → 本区登记 → §4 广播 → 用 send_message 让原 L2 继续
              └─ 其他在跑的 L2：下一轮交互时由 L1 告知，或自行读 §4 发现
```

**禁止**：L2 自己加字段、自己改 `openapi.json`、用"我这边先这么写，回头对齐"的方式绕过。

### 队列

| CR | 提出者 | 请求内容 | 影响范围 | 状态 | 裁决 / 结论 |
|---|---|---|---|---|---|
| CR-001 | （示例，非真实） | `/api/posts` 需要返回作者昵称，契约中无此字段 | `openapi.json`、web | 已批准 | 已加入 `PostVO.authorNickname`；契约 hash 更新见 §4 |

> 状态取值：`待裁决` / `已批准` / `已拒绝` / `已实施` / `已撤回`。
