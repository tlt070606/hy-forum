- `docs/技术方案.md` §5.3 的 SQL 与 `docs/db/schema.sql` **逐行一致**（机器比对，仅顶部注释行差异）——「唯一事实来源」不是口号。

## 2. 结论

**方案骨架站得住，但 v1.3 不能直接冻结 M0。** 存在 3 处 P0 级事实缺陷——不是措辞问题，而是「按文档实施会做不出来或会崩」。其中 2 处（P0-1 收藏表缺失、P0-2 合规留痕无落点）**不在 `docs/README.md` 的「审核建议关注点」8 条清单内**：说明该清单是按设计意图列的，没有下钻到表结构核对。

## 3. P0（已修订）

### P0-1　收藏关系表缺失 → M4 无法验收

**证据**：`PLAN.md` §1.1#7、§2.7、关闭项 C2、M4 四处确认「收藏本期实现」；`技术方案.md` §6.3 有 `GET /api/user/collections`、§6.5 有 `POST/DELETE /api/posts/{id}/collect`、`post.collect_count` 也在表里；但 v1.3 的 14 张表**没有任何收藏关系表**（grep `collect` 全项目只命中 `collect_count` 与接口定义）。`db/README.md` 变更登记里也没有它。

**定性**：功能、接口、计数字段齐全，唯缺关系数据——`collect_count` 是列表页冗余计数，**不能代替关系数据**，因此「我的收藏列表」无数据来源。

**修订动作**：
- `docs/db/schema.sql` 新增表 15 `post_collect`（`uk_post_user` 保证幂等 + `idx_user` 支撑收藏列表分页，结构对齐 `post_like`）；
- `docs/技术方案.md` §5.2 表清单 14→16、§5.3 SQL 块同步、§8.1 标题改为「点赞与收藏幂等」并补收藏；
- `docs/PLAN.md` M0 表数 14→16、M4 验收补「收藏／取消收藏幂等，且『我的收藏』列表与 `post.collect_count` 一致」；
- 走冻结流程：`db/README.md` 变更登记 + `docs/db/migrations/20260914_add_post_collect_and_admin_operation_log.sql`。

### P0-2　合规义务 C9（审核留痕 ≥6 个月）在数据模型中无处落地

**证据**：§10 C9 要求「管理员、时间、对象、动作、理由」保留 ≥6 个月。但 `post`/`comment` 只有 `status`，无审核人信息；14 张表无操作日志表；§6.11 中**每一个需要留痕的动作都没有落点**（帖子审核／置顶／加精／删除、评论删除、用户封禁、配置写入、邀请码与敏感词与版块 CRUD）——只有 `report` 表有 `handle_*` 三个字段。更硬的冲突：§11 写「应用日志保留 30 天」，而 C9 要求 ≥6 个月，两者同时成立必然违规。

**修订动作**：
- 新增表 16 `admin_operation_log`（`admin_id`/`action`/`target_type`/`target_id`/`reason`/`detail`/`ip`/`created_at`，只增不改不删，**无 `is_deleted`**）；
- §10 C9 落地方式改为「写入 `admin_operation_log` **表**，不用文件日志承担留痕义务」；
- §6.11 增加**留痕红线**：写操作同事务落表，处置类 `reason` 必填，留痕失败则整个操作回滚，不得出现「已处置但无记录」；
- §11 与 `deployment.md` §3 修订留存期：应用日志 30 天（仅排障）、**访问日志 ≥6 个月**（不写 180 天——跨 31 天的月份 180 天不足 6 个月）、留痕 ≥6 个月；
- `PLAN.md` M6 验收补「每个动作均可在 `admin_operation_log` 中追溯」。

### P0-3　低配内存预算不闭环：backend 容器 640M 装不下它自己的 JVM

**证据与算术**：v1.3 的 JVM 行在 `deployment.md` **漏了** `-XX:MaxDirectMemorySize=64m`（`技术方案.md` §12 有），两份「唯一依据」不一致。真正的算术是：

```
Heap 448M + Metaspace 128M + Direct 64M = 640M = 容器上限（已用满）
尚未计入：code cache ≈48M + 线程栈（-Xss512k × 线程数；Tomcat 默认 max-threads=200 → ≈100M+）
```

而 v1.3 **从未规定 Tomcat `max-threads` 与 Hikari 池大小**。→ 并发一上来 backend 会被 **cgroup OOMKill**（容器内 OOM，`free -m` 看起来还有余量，极难排查）。若把 backend 抬到 896M，总预算变成 1982M，余量只剩 66M——**即「余量 320M」在旧参数下根本不存在**。

**修订动作**（`deployment.md` §1／§2／§3／§5／§7、`技术方案.md` §11／§12、ADR-0001／ADR-0004）：
- 预算表改为按**进程峰值**推算：MySQL 512M（buffer pool 192M→**128M**）、Redis 96M（maxmemory 96mb→**48mb**）、backend **800M**、nginx 64M、系统 350M → 合计 **1822M／2048M**，余量 **226M**（真实值）；
- backend 800M 构成公开为明细表（堆 384 + 元空间 160 + 直接 48 + code cache 48 + 线程栈 41 + JVM 结构 30 ≈ **711M**，留 89M 尖峰余量）；
- 新增两项必须外置的配置：**Tomcat `threads.max=60`**、**Hikari `maximum-pool-size=8`**；`max_connections` 50→**24**（单后端实例 + 回写任务 ≤12 并发连接）；
- 明确 **JVM 参数单一来源**：只在 `.env` 的 `JAVA_OPTS` 定义，compose 引用，**技术方案与 ADR 一律不复述数值**（本次已把 ADR-0001／0004 的复述数字改为指针）——这是修复漂移的手段本身；
- swap：保留 2G，但补 `vm.swappiness=10` 且各容器 **`memswap_limit == mem_limit`（禁止容器换出）**：放任 JVM／MySQL 换出会让 SerialGC 叠加秒级 STW，比 OOM 更难排查；
- Redis 补**容量依据**（500 用户下总量 <10M，48mb 约 4 倍余量），并要求把 `evicted_keys` 纳入监控——`allkeys-lru` 会淘汰**任意键**，包括登录态 token。

> **残余的不确定性（必须实测）**：Metaspace 160M 是经验区间（Spring Boot 3 + MyBatis-Plus + Sa-Token + Knife4j 通常 90–130M），**首次上线后必须 `jcmd <pid> VM.metaspace` 实测并回填 `deployment.md` §2.2**；镜像分发方式见 P1-14。

**由此暴露并已修复的环境缺陷（记入 [`../agents/README.md`](../agents/README.md) §7）**：

- 本机为 **Windows PowerShell 5.1**（无 `pwsh` 7），系统 ANSI 代码页 **936 (GBK)**。**无 BOM 的 `.ps1` 会被按 GBK 解读**，实测 `verify_m0.ps1` 报 **19 处语法错误、根本无法执行**；加 UTF-8 BOM 后 0 错误。→ 已确立约定：`.ps1` **必须带 BOM**，`.sql`/`.md` **不要带 BOM**；并用 `mysql < file` 而不是 `Get-Content | mysql`（后者会改坏中文种子数据的编码）。
- `PLAN.md` M0 的 DoD 原写 `pwsh -File ...`，本机不可用 → 已改为 `powershell -File ...`。
- 另一处脚本级陷阱：`$ErrorActionPreference='Stop'` 叠加原生命令 `2>&1` 重定向，在 5.1 下会抛 `NativeCommandError`，**恰好会打挂"验证 CHECK 约束真的拒绝非法数据"这一步**（该步依赖 mysql 往 stderr 写错误）。已改为 `Continue` 并用 `$LASTEXITCODE` 判定。

> 这条的价值不在修一个脚本，而在于：**"完成定义必须是一条能跑的命令"这个原则，第一次执行就暴露了 3 个纸面上永远发现不了的缺陷。**
