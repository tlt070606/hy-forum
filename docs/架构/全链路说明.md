# Hy论坛 · 全链路说明（它是怎么跑通的）

> 本文回答一个问题：**从用户在浏览器里点一下，到这个请求真正做完，中间经过了什么、每道安全校验在校验什么。**
>
> **写作依据（重要）**：本文的事实来自**读代码**（`server/src/main/java/**`、`application.yml`、nginx 配置）与**线上实测**（curl 真实接口 / 真实桶）。凡是我**没能独立验证**的，会在文中显式标注「据提交记录」。

| 项 | 值 |

# 二、请求是怎么进来的（部署拓扑）

```
用户浏览器
   │  http://8.138.237.212/            ← 不带端口
   ▼
nginx（80 端口）
   ├─ server_name 8.138.237.212       ← 用 IP 精确匹配到我们这个 server 块
   │      （同机的另一个站点是 80 的 default_server 且没有 server_name → 域名访问照旧走它）
   ├─ location /            → /var/www/hy-forum（H5 静态产物）
   └─ location /api/        → proxy_pass http://127.0.0.1:8080
   ▼
Spring Boot（8080，只在本机）
   ├─ MySQL  127.0.0.1:3306
   └─ Redis  127.0.0.1:6379
```

**两个关键点**：

1. **H5 走同源相对路径 `/api`** —— 后端**没有任何 CORS 响应头**（预检 OPTIONS 会 403），所以前端**必须**经 nginx 同源反代，不能直连后端域名。这也是为什么 `.env.production` 里 `VITE_API_BASE_URL` 对 H5 端**不生效**。
2. **MySQL / Redis 都不对公网暴露**（只 listen `127.0.0.1`），从外网只能访问到 nginx 的 80。

# 三、一次请求的完整链路（四条典型时序）

## 时序 1：打开首页列表

```
浏览器  ──GET /api/posts?sort=latest──▶  nginx ──反代──▶  后端
                                                           │
                                              ① 拦截器：判断这个路径要不要登录态
                                                 （列表是 @OptionalLogin：没 token 也放行）
                                              ② 参数校验 → 查 MySQL（帖子分页）
                                              ③ 组装 PostSummaryVO：
                                                   · 封面/缩略图 URL  ← 读时签名（见 §5.4）
                                                   · liked/collected  ← 相对"当前请求者"，未登录一律 false
                                                   · viewCount        ← 数据库值 + Redis 未回写增量（见 §6.1）
                                                           │
浏览器  ◀── {"code":0,"message":"ok","data":{...}} ─────────┘
```

## 时序 2：登录

```
① 前端拿图形验证码：GET /api/auth/captcha
      → 后端生成 4 位码，存 Redis（TTL 300s），返回 uuid + base64 图片
② 前端提交：POST /api/auth/login {username, password, captchaUuid, captchaCode}
      → 拦截器放行（登录接口在白名单里）
      → 校验验证码（从 Redis 取值比对，一次性消费）
      → 校验口令（BCrypt）
      → StpUtil.login(userId) → 生成 UUID token → 存 Redis（key: hy:token:user:{token}）
      → 返回 {token, ...}
③ 之后每个请求：前端把 token 放进请求头 Authorization
```

## 时序 3：发一条带图帖（**这是全项目最长的一条链**）

```
① 前端 → 后端   GET /api/oss/signature          （要一张"盖章的字条"）
                后端：生成 policy（三条硬约束，见 §5.2）
                     signature = Base64(HMAC-SHA1(Secret, policy))
                返回：host / policy / signature / accessKeyId / dir / expire / callback

② 前端 → OSS    POST https://{bucket}.{endpoint}/    （**文件不经过我们的后端**）
                表单里带：key、policy、OSSAccessKeyId、signature、文件本身、（可选）callback
                OSS：用同一个 Secret 重算签名 → 比对 → 校验 policy 三条约束 → 存下对象

③ OSS → 后端    POST /api/oss/callback           （**服务端到服务端，不是浏览器发的**）
                后端：验签（§5.6）→ 校验对象归属目录与 MIME → 写 post_image（图片记录）

④ 前端 → 后端   POST /api/posts {title, content, images:[...], diskUrl?...}
                后端：写 post（status 由敏感词判定：命中→0 待审）、关联图片、写通知、计数
```

## 时序 4：看图片（读时签名）

```
浏览器 → 后端   GET /api/posts/{id}
                后端返回的 url/thumbUrl **是带签名的临时 URL**：
                  https://{bucket}.{endpoint}/{key}?OSSAccessKeyId=..&Expires=..&Signature=..
浏览器 → OSS    直接 GET 这个 URL → 200 + image/*
```

> **为什么私有桶还要签名**：桶是私有的，裸 URL 一定 403。
> **代价**：URL 会过期、不利于 CDN 长期缓存 —— 这是拿"安全"换"缓存友好"的取舍。

# 四、安全校验体系（六层）

| # | 层 | 校验什么 | 代码位置 |
|---|---|---|---|
| 1 | **密钥不出服务端** | AccessKey Secret 只从环境变量读（`/etc/hy-forum/env`，600）；前端只拿一次性签名 | `OssCredentialProperties`、`application.yml` |
| 2 | **登录态** | token = UUID，存 Redis（`hy:token:user:{token}` / `hy:token:admin:{token}`），有效期 **2 天**（访问续期） | `sa-token` 配置 |
| 3 | **拦截器** | 按路径决定是否要求登录；`/api/admin/**` 走另一套判定 | `common/web/AuthInterceptor` |
| 4 | **注释式放行** | `@OptionalLogin`：登录可选（不报 401） | `common/security/OptionalLogin` |
| 5 | **前后台隔离** | **两套独立 StpLogic**（`loginType=user` / `admin`），不是靠 token 前缀区分 | `SaTokenLogicConfig`、`StpUserUtil`、`StpAdminUtil` |
| 6 | **限流** | 入口维度（IP/分钟）与业务动作维度（如评论/小时） | `RateLimiter` + `RateLimitProperties` |

## 4.1 拦截器的三条边界（**这三条最容易被问**）

取自 `@OptionalLogin` 的类注释，实现也照着走：

1. **没有 token** → 放行并当匿名，**绝不伪造一个用户 id**（不写 `CurrentUser`）；
2. **token 有效但账号被封禁** → **仍然拒绝（1004）**，并且**顺手注销其登录态** ——
   **不降级成匿名**（否则"封禁"就变成可以绕过的软限制）；
3. **不碰后台逻辑** —— `/api/admin/**` 下的接口不可能标 `@OptionalLogin`。

> 补充：**同时标注"必须登录"与"可选登录"时，按"可选"处理**（注释里写了理由）。

## 4.2 前后台为什么必须两套 StpLogic

代码注释原话：**"前后台隔离必须用两套独立 StpLogic，不能靠 token 前缀区分。"**
若共用一个 StpLogic，**管理员登录后拿到的 token 在用户接口上也是合法的** → 越权。

所以：`loginType="user"` 与 `loginType="admin"` 各自独立，Redis key 形如 `hy:token:user:...` / `hy:token:admin:...`。

## 4.3 限流

| 项 | 值 |
|---|---|
| 键格式 | `hy:rl:{action}:{id}`，**时间粒度写在 action 里**（如 `login-ip-1m`） |
| 入口维度 | `hy.rate-limit.ip-per-minute`（登录等） |
| 后台登录 | `hy.rate-limit.admin-login-per-minute` |
| 业务动作 | `hy.rate-limit.comment-per-hour` 等 |
| 超限返回 | **入口维度**：HTTP **429** + `Retry-After` 头；**业务动作维度**：HTTP **200** + 业务码（如 2002） |

> **为什么两种不同**：拦截式限流属于"你请求太频繁"（HTTP 语义就是 429）；业务动作超限属于"业务规则不允许"（前端应该按业务码给文案，而不是当网络错误）。

## 4.4 统一响应与错误码（对外形状）

- 所有响应都是 `{"code":0,"message":"ok","data":...}`；失败是 `{"code":<业务码>,"message":"...","data":null}`
- **HTTP 状态由 `ErrorCode` 决定**，异常可以覆盖它（`httpStatusOverride`）
  > 代码注释原话：**"否则前端就得写两套解析逻辑，契约也就名存实亡。"**
- 用过的一次覆盖：举报限流要用 `429` 这个业务码，但按"业务动作维度"必须返回 HTTP 200 → 用单用途的静态工厂覆盖 HTTP 状态，**未覆盖时行为与从前一字不差**。

## 4.5 内容审核状态机

| status | 含义 | 前台可见性 |
|---|---|---|
| **0** | 待审核 / 尚未人工判定 | **可见**（见下方"重要澄清"） |
| 1 | 正常 | 可见 |
| 2 | 已屏蔽 | **不可见** |

**重要澄清**：可见性规则是 **"隐藏 2"，而不是"必须为 1"** —— 这是当初专门裁定的（否则所有新内容在审核前都对用户不可见，等于发帖没反应）。
后台放行/屏蔽：`status=1 放行 / 2 屏蔽`，**屏蔽必须给 reason**，且**同一事务内写管理留痕**。
举报只登记处置结论，**真正屏蔽内容走帖子/评论的审核端点**（单一写入口原则）。

## 4.6 管理留痕

后台每个写操作落 `admin_operation_log`（谁、什么时候、对谁、做了什么、原因）。
**推荐做法**：所有内容处置都走管理后台 `/admin/`（自动留痕），而不是手写 SQL 改库。

## 4.7 回调验签（RSA）

```
OSS 用自己的**私钥**对回调内容签名 → 回调里带 authorization
我们：从 OSS 公布的地址下载**公钥**（PEM，HTTP 超时 5s）→ 公钥验签
     → 再校验：对象 key 是否落在本站图片目录（只认 post/）、MIME 是否在白名单
     → 都通过才写库
```

**为什么必须验签**：`/api/oss/callback` 是**公网地址**，谁都能 POST。
线上实测：不带签名的 POST → **403 `{"code":403,"message":"回调验签失败"}`**（说明请求到达了后端并被拒，不是 404/502）。

# 五、OSS 直传：完整链路与三个关键设计

## 5.1 为什么直传（而不是后端中转）

- **服务器只有 2 核 1.6 GiB**：文件过服务器会造成内存/带宽峰值（与"禁止在服务器上构建"同源的理由）；
- **代价**是复杂度搬到了四处：**签名 / CORS / 回调 / 读权限**。

## 5.2 policy 的三条硬约束（**不是可选加固，是必须**）

代码注释原话（我在代码里读到的）：

| 约束 | 没有它会怎样 |
|---|---|
| `starts-with $key` = `post/` | **拿到签名的人可以往桶里任意位置写对象** |
| `content-length-range` = `0..5MB` | **一个 1 GB 的文件也能用这份签名上传** |
| `starts-with $Content-Type` = `image/` | **能把桶当网盘用（传 exe/zip）** |

外加：**`expiration`**（ISO8601 UTC，10 分钟）—— 缩短签名被泄露后的可利用窗口。

## 5.3 签名怎么算

```
signature = Base64( HMAC-SHA1( accessKeySecret, policy ) )
```
**Secret 只在服务端出现**：前端拿到的 `policy + signature` **无法反推**密钥。

## 5.4 读时签名（私有桶怎么把图给用户看）

后端在**返回数据时**临时签一个 GET URL：
```
待签串 = "GET\n\n\n{Expires}\n/{bucket}/{key}"
若带图片处理参数，则 x-oss-process 必须算进 CanonicalizedResource
```
**踩过的坑（真实）**：一开始只签了"裸地址"，再把 `&x-oss-process=...` 拼上去 → **403 `SignatureDoesNotMatch`**。
判据来自 OSS 自己回显的 `StringToSign` —— 它**期望**处理参数在待签串里。

## 5.5 目录归属与按用户隔离

| 用途 | 目录 |
|---|---|
| 帖子图 | `post/` |
| 头像 | **`avatar/{用户id}/`** |

**为什么头像要带 userId**：归属校验对头像更严 —— 扁平目录下 **A 能把头像设成 B 上传的对象**。
两条硬约束：
1. **userId 只来自登录态、不接受请求参数**（否则 A 能拿到"往 B 目录写"的签名）；
2. `PUT /api/user/profile` 的 `avatarUrl` **必须落在 `avatar/{自己的id}/` 前缀内**，否则 400。

**并且：目录字面量全项目只在一处定义**（`OssProperties`），签名下发的 `dir` 与后端校验用的前缀由**同一对方法**推导 —— 从构造上不可能不一致。

## 5.6 两种签名，别混

| 场景 | 类型 | 谁有"签名能力" |
|---|---|---|
| 上传（PostObject policy） | **对称** HMAC-SHA1 | 服务端（Secret 不出服务器） |
| 回调（OSS → 我们） | **非对称** RSA | **只有 OSS 有私钥**；我们只有公钥 |

**为什么回调不用对称**：若也用同一把 Secret，**验签方就同时具备了签名能力**（多一条泄露路径）；非对称让"验签方"只有公钥。

# 六、数据与一致性

## 6.1 浏览量（**经典计数题，本项目有真实实现**）

```
写：详情接口只做一次 Redis INCR（hy:post:view:{id}）—— 一次往返、不锁数据库行
落库：每 5 分钟 定时任务 SCAN 扫键 → 原子 GETDEL 取出 → UPDATE MySQL
读：详情页返回 = 数据库值 + Redis 未回写增量  →  实时
    列表页返回 = 数据库值                      →  每 5 分钟跟一次（最终一致）
```
**已知取舍（代码注释里如实登记）**：`GETDEL` 取出后若 `UPDATE` 失败（数据库抖动），**那一批增量会丢**。

## 6.2 计数与关系行必须一致

点赞数 / 收藏数 / 评论数 / 帖子数 / 粉丝数 —— **一律以真实关系行为准**，不做本地推算。
（踩过的坑：评论数一度按 `COUNT(*)` 全量算，把**测试删掉的评论**也算进去了 → 显示 99 而实际 1 条。）

## 6.3 通知

点赞 / 评论 / 回复 / 关注 → 写 `notification`；**自己操作自己 → 不产生通知**；未读数是当前用户的未读。
**点通知跳帖子**（`postId`）；评论类带 `commentId`；**目标被删则显示 404 友好页，但不删通知**（用户的消息记录不该被别人的删除动作抹掉）。

## 6.4 契约：OpenAPI 是唯一事实来源

- 前端类型由契约**自动生成**（`web/src/api/generated/schema.d.ts`）；
- CI 做**契约漂移检查**：仓库快照 vs 运行实例**逐字比对**；
- 契约里的常量（SHA256、路径数）有**机器校验**（不是注释里声称"已校验"）；
- 注意：`servers` 里的 Host/端口**不参与比对**（否则会因为访问方式不同而假红）。

## 6.5 工程约束由机器保证（而不是靠人记）

| 约束 | 谁来拦 |
|---|---|
| 禁止跨模块调用 | **ArchUnit** 架构单测（业务包自动推导；违规直接红） |
| 头像 URL 必须走统一解析器 | **ArchUnit** 规则：domain 与 common.oss 之外禁止直接读 `User.getAvatarUrl()` |
| 接口契约不漂移 | CI 契约比对 |
| 没有硬编码密钥 | CI 密钥扫描 + **pre-commit 钩子**（真实拦下过把 AccessKey 抄进文档） |
| 测试不是空转 | **变异测试**（改坏实现必须变红）+ 验收项↔用例映射表 + 覆盖率缺口脚本 |

# 七、部署与运维

| 环节 | 做法 |
|---|---|
| 构建 | **本机构建** jar 与 H5 产物（**不在服务器上构建**） |
| 上传 | `scp` jar + H5 包 |
| 运行 | systemd `hy-forum.service`（`-Xmx256m -XX:+UseSerialGC`，`Restart=always`），环境变量在 `/etc/hy-forum/env`（600） |
| 调优 | MySQL `innodb_buffer_pool_size=64M`、`performance_schema=OFF`；Redis `maxmemory 64mb`；**2 GB swap** |
| 备份 | 每天 03:30 `mysqldump` → `/var/backups/hy-forum/`，保留 7 天 |
| 回滚 | 换回旧 jar 重启；数据库从备份 `zcat ... | mysql` 恢复 |

**出问题看哪里（对照表）**

| 症状 | 先看 |
|---|---|
| 站点打不开 | `systemctl is-active hy-forum` → 再 `tail /var/log/hy-forum/app.log` |
| 接口 502/504 | nginx 到后端那段（`nginx -t`、后端是否 listening 8080） |
| 图片不显示 | ① 读时签名对不对 ② 桶权限 ③ `x-oss-process` 是否进签名 |
| 上传成功但库里没有 | 回调链路：公网可达 + 验签 + 目录/MIME 校验 |
| 浏览量不动 | Redis 版本（`GETDEL` 需 ≥6.2）+ 定时任务日志 |

# 八、这张图背下来，面试就能讲

```
用户 → nginx(80, IP 精确匹配) → Spring Boot(8080)
                                   ├─ Sa-Token 拦截器（登录态 / 可选登录 / 封禁 1004）
                                   ├─ 业务（MySQL + Redis）
                                   └─ OSS 直传四步：
                                        ① 要签名（policy 三条约束 + HMAC）
                                        ② 浏览器直传 OSS（文件不过服务器）
                                        ③ OSS 回调 → RSA 验签 → 落库
                                        ④ 读时签名 → 私有桶取图
```

**一句话总结这个项目的技术主张**：
> **"把正确性交给约束（契约/架构门/签名/验签），把复杂度留在服务端，把资源消耗（文件、构建）挪出那台 2 核 1.6 GiB 的机器。"**
