## 1. 项目概述

### 1.1 定位

Hy论坛是一个面向中文用户的轻量综合论坛，核心能力为：发帖（图文）、评论（楼中楼）、点赞、关注、个人主页、版块浏览、内容搜索。其中「资源分享」版块支持附带网盘链接与提取码，以卡片形式呈现并支持一键复制。

### 1.2 交付形态

| 端 | 形态 | 说明 |
|---|---|---|
| 网站 | uni-app 编译 H5 | 主站，浏览器访问（仍是 SPA） |
| 安卓端 | uni-app 打包 App | 直接构建，**不再需要 Kotlin WebView 壳** |
| 微信小程序 | uni-app 编译小程序 | **仅练习、不上线**（硬约束见 [`adr/0011`](adr/0011-前端改用uni-app作为唯一前端.md) C1/C2/C4） |

三端**共用同一套 uni-app 前端代码与后端接口**；平台差异通过条件编译（`#ifdef MP-WEIXIN` 等）集中封装，不散落各处。后端**零改动**（小程序端沿用「用户名 + 密码 + 图形验证码」，不接微信授权登录）。

> **v1.15 变更（2026-09-14）**：原为「网站（Vue 3 SPA + PWA）+ 安卓 WebView 壳」，现改为 uni-app 唯一前端三端。破坏性前提消失 → [ADR-0002](adr/0002-前端采用Vue3与Vite与Vant.md) 转「已被取代」，新决策见 [ADR-0011](adr/0011-前端改用uni-app作为唯一前端.md)。

### 1.3 本期不做（Out of Scope）

原生双端 App（iOS）、即时通讯/私聊、支付与虚拟商品、积分等级签到、直播、富文本编辑器、视频上传、多语言、第三方登录（**含微信授权登录**）、全文检索引擎、消息队列、微服务拆分。

> **v1.15**：**微信小程序已移入交付范围**（仅练习，见 §1.2），不再属于"本期不做"。**微信授权登录仍不做** —— 小程序端走用户名+密码，因此不引入 OpenID/UnionID，数据库与后端零改动。详见 [ADR-0011](adr/0011-前端改用uni-app作为唯一前端.md)。

## 3. 技术选型

### 3.1 选型结论

| 层 | 选型 | 版本 | 理由 |
|---|---|---|---|
| 前端框架 | **uni-app（Vue 3 + Vite + TS）** | uni-app 3.x | **唯一前端**，一套代码编译 H5 / 微信小程序 / 安卓。选型见 §3.2 |
| 移动端 UI | **wot-design-uni** | 1.x | Vue 3 + TS 友好；**Vant 4 不能用于小程序端**（小程序无 DOM） |
| 状态管理 | Pinia | 2.x | Vue 3 官方推荐（uni-app 官方支持） |
| 路由 | uni-app 路由 / pages.json | — | 小程序端无 Vue Router，统一用 uni-app 的页面栈 |
| HTTP | **uni.request 封装** | — | 小程序端不能用 Axios（无 XHR）；统一封装请求、鉴权头与错误处理 |
| 后端框架 | Spring Boot | 3.3.x | 需求方指定 Java |
| JDK | OpenJDK | 21 (LTS) | Spring Boot 3 要求 17+ |
| ORM | MyBatis-Plus | 3.5.x | 单表 CRUD 零代码，国内生态好 |
| 鉴权 | Sa-Token | 1.38+ | 轻量、原生支持 Redis 存 token，前后台可配置多套 |
| 接口文档 | Knife4j (springdoc-openapi) | 4.x | 在线调试验证 |
| 数据库 | MySQL | 8.0 | 需求方指定；utf8mb4 / InnoDB |
| 缓存 | Redis | 7.x | 需求方指定 |
| 对象存储 | 阿里云 OSS + CDN | — | 需求方指定；图片直传 |
| 容器 | Docker + Docker Compose | — | 一键部署与迁移 |
| 反向代理 | Nginx | 1.24+ | HTTPS 终结、静态资源、反向代理 |
| 三端打包 | uni-app 打包 H5 / 安卓 / 小程序 | — | 不再需要单独的 Kotlin 壳工程 |

### 3.2 前端选型说明：为什么**改**用 uni-app

> **本节于 2026-09-14 反转。** 原结论是"不用 uni-app，选 Vue3+Vite+Vant 纯 Web + WebView 壳"，其**核心前提是"本项目不做微信小程序"**。该前提已被推翻（要增加小程序端用于练习），因此原结论作废。完整决策见 [ADR-0011](adr/0011-前端改用uni-app作为唯一前端.md)，被取代的原决策保留在 [ADR-0002](adr/0002-前端采用Vue3与Vite与Vant.md)。

**反转的关键**：uni-app **本身即基于 Vue3 + Vite + TS**，两者不是对立语言栈，真正差异只在「能否编译出小程序 / 原生 App」。原方案说"uni-app 只剩原生 App 打包这一个优势"——现在要做小程序，这个优势从"用不上"变成了**唯一能满足需求的选型**。理由链整条反向。

**原决策里哪些判断仍然成立**（不要误以为它们也错了）：

- 论坛的核心交互是信息流滚动 + 图片九宫格 + 楼层评论，**Web 实现体验足够** —— uni-app 本来就是 Web 技术，只是多一层跨端编译。
- **热更新仍然重要，而且不构成反对**：H5 与小程序都不需要用户重装；原方案的安卓端用 WebView 壳加载线上站点，本身也是热更新。

**为小程序端付出的代价（必须承认）**：

1. **H5 端组件生态弱于 Vant** —— wot-design-uni 在 H5 的成熟度与社区资料不如 Vant 4。
2. **需要条件编译**处理平台差异：存储、图片上传、返回键、剪贴板。必须**集中封装**，不能散落各处，否则代码会变得难读。
3. **H5 产物仍是 SPA** —— `PLAN.md` R11（SPA 不利 SEO）风险不变。
4. **小程序端有真实的功能损失**，见 §12。

**三条硬约束（决定了小程序端永远只能练习）**：

| # | 约束 | 后果 |
|---|---|---|
| C1 | 个人主体小程序**不支持 `web-view` 组件** | 不能套站点，小程序页面必须真写 |
| C2 | 小程序 `request` 只允许**已备案 HTTPS 域名** | 本地后端靠开发者工具"不校验合法域名"连通 → **只能停在开发者工具与真机预览** |
| C4 | 个人主体小程序类目不允许「论坛 / 社区」 | 即使将来想上线也上不了 |

> 需求方已知并接受上述三条。**不要把它当"将来能上线的产品"投入精力。**

### 3.3 后端工程结构（建议）

```
hy-forum-server
├── hy-common            通用模块：统一响应、异常、工具、常量
├── hy-domain            实体、Mapper、DTO/VO、枚举
├── hy-service           业务逻辑
├── hy-web-api           面向前台的 REST 接口
├── hy-web-admin         面向管理后台的 REST 接口
└── hy-bootstrap         启动模块、全局配置
```

若追求简洁，也可退化为单体单模块 + package 分层。**建议初期使用单模块 + 分层 package**，避免过度工程化。

**v1.8 补充：包结构与「铁律 3」的落地口径（并行开发的前提，先定死）**

上面的多模块结构是备选；本期采用**单 Maven 模块 + 分层 package**。为了让"禁止跨模块调用"（`AGENTS.md` 铁律 3）**可被自动化校验**，必须先把「模块」在代码上的表达方式定死：

| 项 | 定值 |
|---|---|
| 基础包名 | `com.hyforum` |
| 基础设施 | `com.hyforum.common`（统一响应、异常、工具、常量） |
| 实体 / Mapper / DTO / VO / 枚举 | `com.hyforum.domain` |
| 业务模块（= package） | `com.hyforum.auth`（认证/注册模式/验证码）、`com.hyforum.post`（版块/帖子）、`com.hyforum.media`（OSS 直传）、`com.hyforum.interaction`（评论/点赞/收藏/关注）、`com.hyforum.audit`（敏感词/审核队列/举报）、`com.hyforum.notify`（消息通知）、`com.hyforum.admin`（管理接口与留痕） |

- **铁律 3 的校验方式**：ArchUnit 规则 —— 上列七个业务包**之间禁止相互依赖**，只允许依赖 `common` 与 `domain`。这就是"模块"在单模块工程里的等价物。
- **为什么这样做**：既避免多模块的构建开销，又让铁律 3 变得可自动化校验（而不是靠人记）；将来某个模块膨胀，直接抽成独立 Maven 模块即可，**包名不变、代码不动**。
- 该口径同时是 [`agents/工作计划.md`](agents/工作计划.md) §2「文件所有权表」的基础 —— 每个 L2 Agent 只拥有一个业务包。

## 5. 数据模型

### 5.1 设计原则

- 引擎 InnoDB，字符集 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`，时区 `Asia/Shanghai`。
- 主键统一 `BIGINT UNSIGNED AUTO_INCREMENT`。
- 软删除使用 `is_deleted TINYINT`，配合 MyBatis-Plus 逻辑删除。
- **计数类字段（`post_count`、`like_count` 等）是冗余字段**，用于列表页免聚合查询。见 §8.2 一致性策略。
- 时间字段 `created_at` / `updated_at` 由数据库默认值维护。

### 5.2 表清单（共 16 张）

`user`、`board`、`post`、`post_image`、`comment`、`post_like`、`comment_like`、`post_collect`、`follow`、`report`、`notification`、`admin`、`sensitive_word`、**`sys_config`**、**`invite_code`**、**`admin_operation_log`**

> `sys_config` 存放运行期可调配置（首项即注册模式），`invite_code` 支撑邀请制注册的降级方案，二者详见 §8.8。
> `post_collect` 是收藏关系表（对应 §6.3 的「我的收藏」与 §6.5 的收藏接口）；`post.collect_count` 只是列表页冗余计数，**不构成收藏关系的数据来源**。
> `admin_operation_log` 是管理操作留痕表，承载合规义务 C9（见 §10），只增不改不删。

```sql
-- 5. 评论（两层：主楼 + 楼中楼）
--    P1-3 定案（2026-09-14）：楼中楼的 parent_id 与 root_id **恒等于其所属主楼 id**（归并语义）。
--    由此三层结构在数据上不可能被表达；跨行引用校验见技术方案 §6.6。
-- ---------------------------------------------------------------
CREATE TABLE `comment` (
  `id`               BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `post_id`          BIGINT UNSIGNED NOT NULL,
  `user_id`          BIGINT UNSIGNED NOT NULL,
  `parent_id`        BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '0=主楼；否则为主楼评论id',
  `root_id`          BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '主楼为0；楼中楼存所属主楼id',
  `reply_to_user_id` BIGINT UNSIGNED NULL COMMENT '楼中楼回复的目标用户',
  `content`          VARCHAR(1000)   NOT NULL,
  `like_count`       INT UNSIGNED    NOT NULL DEFAULT 0,
  `reply_count`      INT UNSIGNED    NOT NULL DEFAULT 0 COMMENT '仅主楼维护',
  `status`           TINYINT         NOT NULL DEFAULT 1 COMMENT '0待审核 1正常 2已屏蔽',
  `created_at`       DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `is_deleted`       TINYINT         NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  KEY `idx_post_root` (`post_id`, `parent_id`, `status`, `is_deleted`, `created_at`),
  -- idx_root 必须保留：GET /api/comments/{rootId}/replies 只带 rootId，
  -- 若仅靠 parent_id 查询则必须同时提供 post_id 才能用上 idx_post_root
  KEY `idx_root`      (`root_id`, `created_at`),
  KEY `idx_user`      (`user_id`, `created_at`),
  -- 两层结构的机械不变量（P1-3 定案）：主楼 (0,0)；楼中楼 (主楼id, 主楼id)。
  -- 边界说明：CHECK 只能保证「同一行内两列的关系」，**不能**证明 root_id 指向的那一行确实是主楼
  --          （本项目禁用外键，无法跨行约束）→ 跨行校验必须在**唯一写入口**完成，见技术方案 §6.6。
  CONSTRAINT `chk_comment_two_levels`
    CHECK ((`parent_id` = 0 AND `root_id` = 0) OR (`parent_id` <> 0 AND `parent_id` = `root_id`))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='评论（两层：主楼 + 楼中楼）';

-- 16. 管理操作留痕（v1.4 新增，合规义务 C9）
--     为什么必须独立成表：C9 要求「管理员、时间、对象、动作、理由」保留 ≥ 6 个月，
--     而 post/comment 只有业务状态字段、没有审核人信息，
--     且应用文件日志只保留 30 天（见技术方案 §11）——用文件日志承担留痕义务必然违规。
--     因此留痕走结构化存储：只增不改不删，任何写操作都必须先落本表再返回。
--     action 取值示例：POST_STATUS / POST_TOP / POST_ESSENCE / POST_DELETE /
--                     COMMENT_DELETE / USER_BAN / USER_UNBAN / CONFIG_UPDATE /
--                     INVITE_CODE_CREATE / INVITE_CODE_DISABLE / SENSITIVE_WORD_ADD /
--                     SENSITIVE_WORD_DELETE / BOARD_ADD / BOARD_UPDATE / BOARD_DELETE
-- ---------------------------------------------------------------
CREATE TABLE `admin_operation_log` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `admin_id`    BIGINT UNSIGNED NOT NULL COMMENT '操作人，对应 admin.id（管理员与前台用户隔离，见技术方案 §9）',
  `action`      VARCHAR(40)     NOT NULL COMMENT '动作编码，见上方注释枚举',
  `target_type` TINYINT         NULL COMMENT '1帖子 2评论 3用户 4系统配置 5邀请码 6敏感词 7版块；无具体对象时为空',
  `target_id`   BIGINT UNSIGNED NULL COMMENT '对象主键；无具体对象时为空',
  `reason`      VARCHAR(200)    NULL COMMENT '处置理由；屏蔽/封禁/删除类动作必填（合规要求可追溯处置依据）',
  `detail`      VARCHAR(500)    NULL COMMENT '变更摘要，如 status:1->2、register_mode:open->invite',
  `ip`          VARCHAR(45)     NULL COMMENT '操作来源 IP，45 字符以兼容 IPv6',
  `created_at`  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  -- 「某个管理员做过什么」：后台按操作人追溯
  KEY `idx_admin`  (`admin_id`, `created_at`),
  -- 「某个对象被谁处置过」：管理员查看帖子/用户的处置历史
  KEY `idx_target` (`target_type`, `target_id`, `created_at`)
  -- 注意：本表无 is_deleted。留痕记录不可删除，清理只能按 created_at 滚动淘汰 ≥ 6 个月之前的数据
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='管理操作留痕（合规 C9，保留 ≥ 6 个月）';
```

### 5.5 网盘字段设计专项说明

需求方提出「网盘链接是否已包含提取码」。结论：**不能合并为一个字段**，理由如下：

| 网盘 | 链接形态 | 是否含提取码 |
|---|---|---|
| 百度网盘 | `https://pan.baidu.com/s/1aBcDeFgHiJ` | 默认不含；开启后可带 `?pwd=abcd` |
| 阿里云盘 | `https://www.alipan.com/s/xxxx` | **无提取码机制** |
| 夸克网盘 | `https://pan.quark.cn/s/xxxx` | **无提取码机制** |
| 115 / 天翼 / 迅雷 | `https://115.com/s/xxxx` 等 | 有独立访问码 |

因此：

1. `disk_url` 与 `disk_code` **分开存储**，`disk_code` **可为空**（阿里云盘/夸克场景）。
2. 后端在保存帖子时执行**归一化**：若 `disk_url` 中携带 `pwd=` 查询参数，则正则解析出提取码自动写入 `disk_code`，并将 `disk_url` 规范化为不含 `pwd` 的干净链接；两者始终保持一致。
3. 前端渲染逻辑：
   - `disk_code` 非空 → 渲染「链接 + 提取码 + 一键复制整段」卡片；
   - `disk_code` 为空 → 仅渲染「打开链接」按钮，不显示提取码区域。
4. 一键复制的内容格式（拼接后写入剪贴板）：

```
链接：{disk_url}
提取码：{disk_code}
来自 Hy论坛
```

> 说明：Web 端无法直接跳转网盘 App，复制后由用户自行粘贴。此为浏览器沙箱限制，属预期行为，需在 UI 上给出明确引导文案。

## 6. 接口设计

### 6.1 通用约定

- 统一前缀：前台 `/api`，后台 `/api/admin`。
- 统一响应体：

```json
{ "code": 0, "message": "ok", "data": {} }
```

- 分页响应：`{ "code": 0, "data": { "list": [], "total": 0, "page": 1, "size": 20 } }`
- 鉴权：请求头 `Authorization: {token}`（Sa-Token）。需要登录的接口在前台与后台分别校验。
- 错误码：`0` 成功；`400` 参数错误；`401` 未登录；`403` 无权限；`404` 资源不存在；`429` 请求过于频繁；**`500` 服务器内部错误（兜底，见下）**；`1001` 用户名已存在；`1002` 用户名或密码错误；`1003` 验证码错误；`1004` 账号已被封禁；`2001` 内容包含敏感词；`2002` 发帖过于频繁。

  > **关于 `500`（CR-003 裁决，2026-09-14：批准登记）**：这是**兜底码**，用于未被业务异常覆盖的运行时错误。
  > 不加它的话，未捕获异常会漏出 Spring 默认错误体，**破坏本节的统一响应约定** —— 这是必须堵的洞，因此登记进契约。
  > **但必须遵守两条约束**：
  > 1. **响应体只给通用文案**（如"服务器内部错误"），**绝不含堆栈、SQL 报文、类名、参数值**。细节写服务端日志。
  > 2. 兜底不是借口：**能归到具体业务码的错误一律用具体码**（如用户名重复必须是 `1001`，不能图省事返回 `500`）。

### 6.6 评论模块

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/posts/{id}/comments` | 否 | 主楼分页列表（含每条主楼的前 2 条楼中楼预览） |
| GET | `/api/comments/{rootId}/replies` | 否 | 某主楼下的全部楼中楼，分页 |
| POST | `/api/comments` | 是 | 参数：postId、parentId（0=主楼）、content、replyToUserId（可选） |

**层级约束（P1-3 定案，2026-09-14）**：仅支持两层，采用**归并语义**：

| 场景 | `parent_id` | `root_id` |
|---|---|---|
| 主楼（直接评论帖子） | 0 | 0 |
| 楼中楼（回复主楼） | 主楼 id | 主楼 id |
| 「回复某条楼中楼」 | **归并为**主楼 id | 主楼 id（被回复者由 `reply_to_user_id` 记录） |

即：**楼中楼的 `parent_id` 与 `root_id` 恒等于其所属主楼的 id**。因此 `GET /api/comments/{rootId}/replies` 里的 `rootId` 指的是**主楼评论 id**（也就是楼中楼行的 `root_id` 值）。

**「真正杜绝三层」由三层机制叠加保证，缺一不可 —— 只靠 CHECK 是不够的：**

1. **数据库 CHECK 约束** `chk_comment_two_levels`（见 §5.3）：保证同一行内 `parent_id`/`root_id` 的关系不变量（主楼 `(0,0)`、楼中楼 `(x,x)`）。它拦得住"字段填错"，**拦不住"指向了错的楼层"**。
2. **唯一写入口的应用层校验**：评论写入必须只有一个入口，流程固定为「加载被回复评论 → 若其 `parent_id != 0`，则取该行的 `root_id` 作为 `parent_id` → **并校验目标行的 `parent_id = 0`（确实是主楼）** → 落库」。**禁止任何其他代码路径直接 `INSERT comment`**，否则"指向楼中楼"会绕过校验。
3. **测试**：`M4_comment_no_third_level`，必须包含对抗性用例（直接对楼中楼再回复、伪造 `parentId` 指向楼中楼），见 [`testing/验收项-测试映射.md`](testing/验收项-测试映射.md)。

> **为什么不能只靠数据库**：本项目**禁用外键**（[`db/README.md`](db/README.md) 基线），而 `CHECK` 无法跨行引用，所以「`root_id` 指向的那一行必须是主楼」这一条**无法在数据库层单点保证**。因此把校验收敛到唯一写入口是**架构要求，不是编码习惯**。若将来允许外键，可补 `root_id → comment.id` 的引用约束，把这一条也机械化解掉。

## 7. Redis 设计

| Key 模式 | 类型 | TTL | 用途 |
|---|---|---|---|
| `hy:captcha:{uuid}` | String | 300s | 图形验证码答案 |
| `hy:token:*` | String | 随会话 | Sa-Token 登录态存储 |
| `hy:post:view:{postId}` | String | 持久 | 浏览量增量计数，定时批量回写 MySQL |
| `hy:post:detail:{postId}` | String(JSON) | 1800s | 帖子详情缓存，帖子更新/删除时主动失效 |
| `hy:board:hot:{boardId}` | ZSET | 1h | 版块热榜，score = like*3 + comment*5 + view*1 |
| `hy:rl:{action}:{userId 或 ip}` | String | 60s | 接口限流计数 |
| `hy:user:brief:{userId}` | String(JSON) | 600s | 用户简要信息缓存（昵称/头像） |

**定时任务**：每 5 分钟将 `hy:post:view:*` 批量回写至 `post.view_count`。

**缓存边界（对应 1000 条数据规模）**：

- **做**：详情页缓存、浏览量增量、热榜 ZSET、用户简要信息缓存。这些在 1000 条量级下已能实际减少数据库压力。
- **不做**：列表页缓存（分页维度多、失效条件复杂，收益抵不上维护成本）、多级缓存、Redisson 分布式锁、缓存预热、布隆过滤器。这些在单机 1000 条规模下属于过度设计。

## 8. 关键业务规则

### 8.1 点赞与收藏幂等

依赖 `post_like` / `comment_like` / `post_collect` 的**唯一索引** `UNIQUE(post_id, user_id)`。实现方式：`INSERT` 时捕获 `DuplicateKeyException` 视为「已点赞 / 已收藏」，直接返回成功；取消点赞或取消收藏时 `DELETE` 影响行数为 0 也返回成功。**不使用**「先查询再判断」的两步式实现，避免并发下的竞态。

> 收藏之所以复用同一套幂等机制，是因为 `post_collect` 的 `uk_post_user` 与 `post_like` 结构完全一致（见 [`db/schema.sql`](db/schema.sql) 表 6 与表 15）；两者都需要在**同一事务**内维护对应的冗余计数字段（`post.like_count` / `post.collect_count`）。

### 8.2 计数一致性策略

- 写操作在**同一事务**内完成「关系表写入 + 计数字段增减」。
- 计数字段只做**增减运算**（`SET like_count = like_count + 1`），不做 `SELECT` 后回写。
- 提供**管理员手动触发的计数校准任务**，用于修复极端情况下的不一致。

### 8.3 浏览量

详情接口**不直接 UPDATE 数据库**，而是 `INCR hy:post:view:{postId}`，由定时任务批量回写。这是 Redis 在本项目中最主要的实际价值。

### 8.4 图片直传 OSS

1. 前端调用 `GET /api/oss/signature`（需登录）获取签名。
2. 前端**直传** OSS，不经过后端服务器，节省带宽。
3. OSS 回调 `POST /api/oss/callback`，后端验签后写入 `post_image` 表。
4. 用户提交帖子时，只提交图片 URL 列表，后端校验 URL 归属（必须位于本项目 OSS 目录前缀内），防止用户提交外部恶意链接。

**安全红线**：AccessKey **绝不写入前端代码或 APK**，APK 可被反编译。必须使用服务端签名。

**OSS 配置要求**：配置 CORS 允许站点域名；限制上传大小（单图 ≤ 5MB）；限制 Content-Type 白名单（`image/jpeg`、`image/png`、`image/webp`、`image/gif`）；对缩略图使用 OSS 图片处理参数生成，减少流量。

### 8.5 首页双流

- **关注流**：`SELECT ... WHERE user_id IN (SELECT target_user_id FROM follow WHERE user_id = :me) ORDER BY created_at DESC`。
- **全部流**：`SELECT ... WHERE status=1 AND is_deleted=0 ORDER BY created_at DESC`，并额外提供「热门」排序入口（按 `like_count*3 + comment_count*5 + view_count` 排序）。
- 未登录用户点击「关注流」时，引导登录。

### 8.6 内容审核流程

1. 用户提交帖子/评论 → 后端执行**敏感词匹配**（`sensitive_word` 表，服务启动时加载进内存，如 DFA 算法）。
2. 命中敏感词 → **帖子与评论均置 `status=0`（待审核）**，不对普通用户展示，进入后台审核队列。处理入口必须成对存在：帖子走 `PUT /api/admin/posts/{id}/status`，评论走 `PUT /api/admin/comments/{id}/status`（见 §6.11）——**队列必须有出口**，缺任一入口都会导致待审内容既无法放行也无法屏蔽。
3. **审核能力抽象**：定义 `ContentAuditService` 接口（`auditText` / `auditImage`），默认实现为「敏感词 + 人工队列」。因个人资质能否开通阿里云内容安全**尚不确定**，本期**不依赖任何第三方机审服务**，但接口预留到位——将来若开通，新增一个实现类即可切换，**不改动业务代码**。
4. **图片审核（2026-09-15 澄清，见 CR-006）**：`post_image.audit_status` 的取值语义为
   **`0` = 尚未被人工判定（默认）／ `1` = 已人工确认通过／ `2` = 已判定违规**。
   **前台的可见性规则是「隐藏 `audit_status = 2`」，不是「必须为 1 才显示」。**
   理由：本期**没有图片机审能力**（第 3 条的 `ContentAuditService.auditImage` 只是预留，本期不依赖第三方服务），
   若规定"默认 0 = 待审、必须人工放行才可见"，则**每张图都要人工点一次**，
   与第 5 条的「未命中敏感词的帖子**先发后审**」直接矛盾，且 M3 的验收（"带图资源帖在详情页正确展示"）无法达成。
   **图片的审核出口**（管理端查未判定图片、置 1 或 2）归 **M5 / M6**，M3 不实现；M3 只负责"写入 + 前台不隐藏未判定图片"。
   此条与第 2 条"**队列必须有出口**"是同一个道理：**不能建一个只进不出的队列** ——
   差别在于图片这一队列的出口在 M5/M6，因此 M3 阶段**不把未判定的图片挡在前台之外**。
5. **降级策略**：**未命中敏感词**的帖子先发后审（`status=1` 直接可见），依靠用户举报 + 管理员巡查。此策略需在运维层面明确记录。
6. **编辑重审（状态机闭环）**：帖子内容经 `PUT /api/posts/{id}` 变更后，`status` **一律回到 0** 并重新入队（见 §6.5）。原因：在「先发后审」模式下若不重置状态，作者可先发布合规内容取得 `status=1`，再改写为违规内容，从而同时绕过敏感词过滤与管理员巡查 —— 这是审核链上的一条真实绕过路径，必须由状态机堵住，不能靠约定。评论本期不支持编辑，故无此问题。

### 8.7 频率限制

| 行为 | 限制 |
|---|---|
| 发帖 | 新注册用户 24 小时内 ≤ 3 帖；普通用户 ≤ 10 帖/小时 |
| 评论 | ≤ 20 条/小时 |
| 举报 | ≤ 10 次/天 |
| 登录 | 同一 IP ≤ 10 次/分钟 |
| **单 IP 全站请求（每日）** | ≤ 3000 次/天 —— 保护 2 核 2G 单机 |
| **单用户全站请求（每日）** | ≤ 1000 次/天 |

基于 Redis `INCR` + `EXPIRE` 实现。日维度使用 `hy:rl:daily:{scope}:{id}:{yyyyMMdd}` 键，TTL 48 小时。

**超限行为** —— ⚠️ **2026-09-16 改准**：原文只有一句「返回 `429` 与 `Retry-After`」，
把**两个不同层面**的超限说成了一件事，与已实现的代码不符（M3 实现者按原文读会写错）。
实际分两层，**不要混为一谈**：

| 超限发生在哪一层 | 返回 | 现状（**以 `common/api/ErrorCode.java` 为准**） |
|---|---|---|
| **入口维度**：同一 IP 登录、单 IP 全站、单用户全站 | **HTTP 429** + `Retry-After` 头 | `ErrorCode.TOO_MANY_REQUESTS(429, …, HttpStatus.TOO_MANY_REQUESTS)` 已实现；**`Retry-After` 头尚未设置**（M1 只把重试秒数写进了 message）→ 见交接事项 **H2**，归 M5 的统一限流切面 |
| **业务动作维度**：发帖次数、评论、举报 | **HTTP 200 + 业务码**（发帖超限 = `2002 发帖过于频繁`） | `ErrorCode.POST_TOO_FREQUENT(2002, "发帖过于频繁", HttpStatus.OK)`；M3 已实现并有**真实触发**用例（`M3_post_rate_limit_triggers_2002`，含"没落库"与"换了老用户就不受影响"两条反证）。评论 / 举报归 M4 / M5 |

**为什么业务动作维度不用 429**：那一层的含义不是「请求被打回」，而是「**这个动作现在不能做**」——
请求本身合法、服务端也**接受并处理了**它，只是这个业务动作被拒绝。它与「帖子命中敏感词（`2001`）」
属于同一类语义，因此走统一响应体的业务码（§6.1），HTTP 仍是 200。
入口维度正相反：那是**与业务语义无关的准入限制**，用 HTTP 状态码表达才对。

> **是否把两层统一为 429 由 M5 统一限流切面一并决定**（H2）。
> **在决定之前不要单方面改任何一侧** —— `ErrorCode` 的取值属 M1 冻结的定义，改它要走 CR。

前端对两种超限都要给友好提示，**不做自动封号**（避免误伤正常用户）。

### 8.8 注册模式与邀请码

注册模式存放于 `sys_config` 表的 `register_mode` 配置项，取值：

| 取值 | 行为 |
|---|---|
| `open`（默认） | 任何人可注册，需通过图形验证码 |
| `invite` | 必须提供有效邀请码才能注册；用于论坛社区备案受阻时的降级 |
| `closed` | 完全关闭注册，仅保留已注册用户登录 |

**设计要点**：

- 注册接口在 `invite` 模式下额外校验 `inviteCode`。**并发正确性必须靠「条件更新 + 影响行数校验」，不能靠 `uk_code`**（P1-4 修订，2026-09-14）—— `uk_code` 只保证 code 不重复，**不保证不被使用两次**；而「先 `SELECT` 查 `status=0` 再 `UPDATE ... WHERE id=?`」在 RC/RR 隔离级别下，两个并发事务**都可能成功**。正确写法：

  ```sql
  -- 顺序：先 INSERT user 拿到 id → 再条件更新邀请码 → 影响行数必须为 1
  UPDATE invite_code
     SET status = 1, used_by_user_id = :uid, used_at = NOW()
   WHERE code = :code
     AND status = 0
     AND (expire_at IS NULL OR expire_at > NOW());
  -- 影响行数 = 0 → 抛业务异常并回滚整个注册事务
  -- （码已被使用 / 已失效 / 已过期，三种情况在此一并拒绝）
  ```

  InnoDB 的 `UPDATE` 是**当前读**：第二个并发事务会看到已提交的 `status=1`，`WHERE` 不再匹配 → 影响行数 0 → 回滚。**这才是真正的并发防线**，并由 `M6_invite_code_single_use_concurrent` 验证。
- 前端通过 `GET /api/auth/register-mode` 获取当前模式，动态决定是否渲染邀请码输入框，**无需发版**即可切换。
- 邀请码由管理员在后台生成，可设置有效期，默认一次性使用。
- 管理员账号不受注册模式影响，可随时新增。

## 9. 安全设计

| 风险 | 应对措施 |
|---|---|
| 密码泄露 | BCrypt（strength=10）哈希存储，禁止明文与可逆加密 |
| 越权操作 | 所有写接口校验资源归属（`post.user_id == currentUserId`） |
| SQL 注入 | MyBatis-Plus 参数化查询，禁止字符串拼接 SQL |
| XSS | 帖子/评论内容**按纯文本 + 换行**处理，前端渲染时转义；**本期不引入富文本/Markdown**，规避 XSS 面 |
| CSRF | 采用 Token 鉴权（非 Cookie-Session），天然免疫 |
| 文件上传 | 类型白名单 + 大小限制 + 对象名 UUID 化 + 禁止可执行后缀 |
| 接口刷量 | Redis 限流（见 §8.7）+ 图形验证码 |
| 账号安全 | 登录失败次数限制，连续失败锁定 15 分钟 |
| 后台隔离 | `admin` 表与 `user` 表完全隔离，Sa-Token 配置独立 StpLogic |
| 日志脱敏 | 生产日志不得输出密码、token、AccessKey |

## 10. 内容安全与合规义务

本项目为**开放注册的 UGC 论坛**（注册模式可后台切换为邀请制），需承担如下义务，均为上线**前置条件**：

| # | 义务 | 依据 | 落地方式 |
|---|---|---|---|
| C1 | 用户协议、隐私政策，注册时勾选同意 | 《个人信息保护法》 | 静态页 + 注册页强制勾选（后端校验 `agreeProtocol`） |
| C2 | 违法信息处置：发现即停止传输、保存记录、报告 | 《网络安全法》第 47 条 | 敏感词过滤 + 举报机制 + 后台屏蔽/删除 + 操作留痕 |

| C5 | 公安联网备案 | 《计算机信息网络国际联网安全保护管理办法》 | ICP 备案通过后 30 日内办理 |

| C9 | 内容审核操作留痕 | 《网络安全法》 | 审核动作写入 **`admin_operation_log` 表**（管理员、时间、对象、动作、理由、来源 IP），只增不改不删，保留 ≥ 6 个月。**不用应用文件日志承担留痕义务** —— 应用日志仅保留 30 天（见 §11），若以文件日志承担 C9 必然违规。后台接口的留痕要求见 §6.11 |

但必须明确：**邀请制与不公开推广只降低被发现的概率，不构成法定豁免** —— C1、C5、C6、C9 等义务以及跟帖评论的实名义务并不因邀请制而免除。因此该降级方案在本项目中的定位是 **残余风险接受（residual risk accepted）**，**不是合规达成**；评审与后续运营都不得把它当作已完成项。

**Docker Compose 服务清单**：`nginx`、`backend`、`mysql`、`redis`（**单一 compose 文件，无档位**）。

**参数与容量**：**本节不复述任何内存／参数数值。** 全部参数（MySQL、Redis、JVM、Tomcat、Hikari、容器 `mem_limit`）的唯一来源是 [`ops/deployment.md`](ops/deployment.md) §2。该文档目前是**一份统一配置**（开发与上线共用，仅环境相关项经 `.env` 注入），并含「2 GiB 应急参数集」附录 A。取消档位的决策依据见 [`adr/0010-部署以本地开发为基准并取消档位.md`](adr/0010-部署以本地开发为基准并取消档位.md)。

**两条恒定硬性约束（与规格、档位无关）**：

1. **禁止在服务器上执行构建**（`AGENTS.md` 铁律 6）。`mvn package` 与 `npm run build` 的内存峰值均在 1G 以上，会直接把低配服务器打挂。正确做法是**本地或 CI 构建 JAR／`dist`／镜像后上传**；镜像分发方式见 [`ops/deployment.md`](ops/deployment.md) §4.2。
2. **图片必须走 OSS + CDN**，不能由 ECS 直接对外提供图片流量 —— 带宽与内存都会被拖垮。

**容量规划**：开发期不设内存约束；**上线前**按 [`ops/deployment.md`](ops/deployment.md) §6 回填目标规格并复算参数、回填该文档参数表。**若最终目标仍为 2 GiB，必须整体启用该文档附录 A** —— 含 2G swap、`vm.swappiness=10`、`memswap_limit == mem_limit`（禁止容器换出）与 A.1 的整套参数，缺一不可。

**扩容优先级**（按性价比排序）：内存 ＞ 将 MySQL 迁至云数据库 RDS ＞ 升级带宽。

**三端打包与平台差异要点（v1.15 改写）**：

> 原内容为「安卓 APK 的 WebView 壳要求」（`shouldOverrideUrlLoading` 拦截、物理返回键、启动页等）。改用 uni-app 后**不再需要 Kotlin 壳**，那六条随之作废。以下是新的要点。

1. **产物**：`uni-app` 一次代码输出三份 —— H5 `dist`（交给 Nginx）、安卓包（`uni-app` 内置打包，云打包或离线打包）、小程序包（微信开发者工具上传）。
2. **网盘链接的处理方式变了，且小程序端有真实损失**：

   | 端 | 用户点网盘链接后 | 说明 |
   |---|---|---|
   | H5 | 打开新标签页 | 正常 |
   | 安卓 App | 交给系统浏览器或对应网盘 App（`plus.runtime.openURL`，`#ifdef APP-PLUS`） | 与原来一致 |
   | **微信小程序** | **只能复制链接，无法跳转到外部浏览器** | 小程序没有 `web-view`（C1），也不能唤起系统浏览器。**这是小程序端的真实功能损失，需求方已知并接受** |

   > 后续可考虑用 `wx.navigateToMiniProgram` 跳转网盘官方小程序，但需要对方的 appId 且各网盘支持情况不一，本期不做。因此小程序端的网盘卡片文案要明确写"已复制，请到网盘 App 粘贴打开"，**不要写"点击打开"**。
3. **返回键 / 启动页 / 状态栏**：由 uni-app 与各端默认行为处理，无需自己写原生代码；但要**在真机上验证首页按返回键的退出行为**（M7 验收项）。
4. **权限与隐私合规**：安卓打包后需配置隐私政策弹窗与所需权限声明（安卓 12+ 对相册/相机权限有硬性要求）。这部分与 §10 的合规义务相关，**不能因为"本地可用版"就省掉**。
5. **打包产物同样可被反编译** —— **绝不把 AccessKey / AppSecret / 任何密钥放进前端代码**（铁律 5、8）。小程序与 App 端上传图片一律走服务端签名直传，与 H5 完全一致。

**域名与证书**：使用阿里云免费 DV 证书或 Let's Encrypt（自动续期）。
